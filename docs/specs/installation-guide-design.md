## 3. 本轮推荐设计

### 用户补充：方便安装与自由配置优先（2026-10-08）

用户明确要求：安装部署不要太多限制、校验机制，要方便更改端口等配置。此前方案中的证据核对是文档作者的责任，不应转化为安装者必须完成的一套检查流程。

- 主线只保留真正需要的安装、配置、启动步骤；不新增预检脚本、manifest/hash 校验门槛、版本审批、镜像白名单、端口白名单或配置锁定，也不要求安装者重复执行启动脚本已有的检查。
- 默认值只是开箱即用的起点，不是必须遵守的部署方式。端口、监听地址、镜像名、数据库和数据目录允许按需配置，优先复用现有入口，不另造配置层。默认镜像名也只是减少配置的便利选项，不要求所有人改名。
- 在安装主线附近增加“改端口和常用配置”短节，用具体示例说明临时参数与持久配置：首次启动可用 `./deploy/start.sh --host 0.0.0.0 --port 8080`；持久设置只编辑 `runtime/arena.env` 的 `ARENA_SERVER_HOST`、`ARENA_SERVER_PORT`，命令行优先。示例里的 8080 不是唯一允许端口，不要求改源码或重建镜像。
- 已运行实例更改地址、端口或环境配置时，示例使用 `stop.sh` 后 `start.sh`，让 Server 与 Dispatcher 一起加载新配置；提醒会中断服务即可，不另加审批或强制检查清单。临时参数不会写回配置文件，下次未传参数时恢复文件值。
- 本机访问在 Origin 未自定义时会随端口自动生成 localhost/127.0.0.1 Origin，不要求重复填写。局域网/域名访问给一个具体 `CAIRN_TRUSTED_ORIGINS=http://192.168.1.10:8080` 示例并注明替换实际地址；已经自定义 Origin 时端口变化须同步修改。把现有行为说清，不扩展为公网安全加固教程，也不借本轮删掉现有认证或 Origin 检查。
- 常用配置用一张小表写清“在哪里改、如何生效”；外部数据库、存储和镜像映射细节按需查阅，不塞进每个人的首次安装流程。兼容性/标签诊断放排障，发布来源未确认用一句话说明，不让限制说明淹没安装步骤。

依据：`deploy/start.sh:9-18,52-56,133-145,208-239`；`deploy/common.sh:322-362`。这是文档设计纠偏，不是授权实施会话顺手改部署逻辑。若发现现有逻辑确实妨碍常用配置，单独记录最小问题，再决定是否开下一轮代码改动。

### 单一指南，两条明确路径

继续使用 `docs/deployment-linux-zh.md` 作为唯一完整安装入口，README 保留短介绍与醒目链接。不要另建 quickstart、安装报告或同义指南。正文先给最短安装主线，低频配置放后面；简洁靠复用共同步骤，不靠删除必要前提。

开头用小表解释选择：

1. **使用已有 Worker 镜像安装（有条件）**：需要与应用版本及主机架构匹配的可信镜像，以及应用程序文件。优先描述“应用部署包 + 已有 Worker 镜像”，明确仍需宿主 Python/uv、Docker 和数据库；若只有源码没有部署包，还需构建前端。不能称作纯镜像、全栈 Compose 或完全离线安装。
2. **从源码完整安装（当前可自构建路径）**：获取源码、安装 Python 依赖、构建正式前端、构建 Worker、启动完整系统。

没有可信预构建镜像时明确引导第二条，不把本地 build 偷换成“官方镜像安装”。本轮不新增全栈容器化、镜像发布流水线或下载渠道；若用户后续确实要求无需源码/宿主 Python 的全镜像产品，那是独立实现需求。

### 必须写全，但不展开为运维手册

- **前置条件按路径拆分**：共同宿主条件、源码额外 Node/npm/Git、ZIP 解压工具、Worker 本地构建的网络与资源条件。建议主线使用 Node 24 LTS；不要编造测试过的最低硬件规格或架构兼容承诺。对系统依赖给明确官方安装入口或一个限定发行版的示例，不写适用于所有 Linux 的万能安装命令。
- **应用文件来源**：源码地址沿用仓库已有来源；部署包是 `package_release.py` 生成的 `arena-<version>-linux-code-only.zip`，不是 GitHub 自动 Source code ZIP。说明从可信分发方取得匹配包；没有已核实下载地址就明确标注，不捏造 Release。包的生成命令移到可选说明，不要求安装者先自行构建才能理解镜像路径。
- **已有镜像**：分别给 `docker pull` 和可信离线 tar 的 `docker load` 用法，明确地址/文件路径为待替换参数，不是已发布资产。导入后使用实际镜像名；新安装可选标为默认 `arena-worker:local` 以减少 YAML 操作，不强制改名、不盲目覆盖既有 tag。保留自定义引用时说明修改完整配置中的 container.image；已有显式 images/profile 映射的情况放进阶说明。不把手动标签、摘要、架构逐项校验设为启动前置步骤，实际兼容错误放排障。
- **步骤顺序**：获取应用 → 准备依赖/配置 → 准备匹配镜像 → 配置必要访问地址/数据库 → 启动 → 登录与基础状态检查。每个代码块标明工作目录、先决条件和变量替换，区分可复制命令和二选一分支。解压放入独立新目录，不覆盖现有安装。
- **默认主线**：使用脚本管理的 PostgreSQL，毋须手工重复生成数据库密码、keyring、token 或 schema。外部 PostgreSQL 和局域网访问放短可选小节；远程 Origin 配置要在首次远程登录前可见，不能只写“开放 8000 端口”。
- **共同首次使用**：默认 URL、admin 账号、两种随机密码交付方式、改密；按当前界面配置 Models/Workers、启用并绑定模型、检查 Dispatcher 心跳。模型凭据在界面保存，不让新用户同时填写旧 providers/workers YAML。创建项目、模型测试可能产生费用，不作为安装自动验收命令。
- **状态与运维**：列 start/status/logs/stop，解释 running、heartbeat、server-only 的边界；源码与部署包更新分开，说明修改运行配置后按需 stop/start、Worker 同名 tag 与存量容器不会自动刷新。保留数据库、数据目录、runtime 配置、keyring/token 的保护要求，不给清库或全局 prune 命令。
- **简短排障**：保留依赖/网络下载、数据库、静态资源、Origin、镜像不匹配、Worker/心跳和 keyring 的直接定位，不掺入发现算法、浏览器协议细节或大段发布治理。

### 8.3 最小实现：保留一个更新入口

1. 保留部署包更新主线，不要求用户另外手工执行 `docker build` 或数据库迁移。推荐顺序为：现有暂存与停止 → 替换受管文件 → install → **准备本次 Worker** → start（含既有数据库迁移）→ status。Worker 准备失败必须非零退出，不继续迁移、启动新应用并静默沿用旧 Worker。
2. 新 Worker 准备在目标安装目录的**新子进程**执行，加载新 `common.sh`、新 `.venv` 和该安装的运行环境；不能调用更新器当前 shell 已加载的旧 helper。沿用现有锁与参数转发方式，避免新 helper 重入更新锁造成死锁；保留 `--server-only` 的明确跳过语义。
3. 用现有 `DispatchConfig` 解析实际镜像引用。默认本地管理的 `arena-worker:local` 即使存在也走带缓存的本次构建，不以三个固定版本标签判断无须更新。必要的镜像解析由 update / start 共用，修正本轮会影响实际更新目标的引用不一致，不扩大为全部画像系统重构。
4. 构建先产出候选镜像，通过既有镜像 / 应用自检后才更新实际使用的本地 tag；失败不覆盖原可用引用，不删除旧镜像或清缓存。构建通过只说明新镜像已准备，不说明旧容器或真实任务已升级。无需新增发布 manifest、版本审批或通用镜像管理平台。
5. 自定义镜像名、远端 tag/digest、显式 images / profile 不静默改成默认值，不把本地 runner 覆盖到任意用户镜像。本轮自动构建保证针对实际使用的默认本地镜像；用户维护的其他引用保留，清楚报告“未自动更新，需要配套镜像”。现有兼容检查不是版本配套证明，不能把这类结果显示为“全部 Worker 已升级”；若实际配置无法供启动使用，应明确失败，不回退默认镜像。第 7 节未确定的 registry 不作为本轮前提。
6. 失败提示和修复后续命令也必须覆盖 Worker 准备步骤，不能引导用户绕过它直接 start。应用、依赖、Worker、数据库初始化和服务状态的完成范围分别如实报告，不新增需要用户手工维护的重复状态文件。

### 8.4 最小分层调整与缓存承诺

沿用当前多阶段 Dockerfile，不新建独立工具镜像发行体系，不变更现有工具版本、安装来源、依赖集合或补丁行为：

- 将与 runner 无关的 MCP 安装、Playwright 补丁、CLI 初始化、目录 / 配置 / git 初始化移到应用 COPY 之前。保持 root / kali 用户、权限、浏览器路径和禁用自动更新等运行语义；从混合 RUN 中拆出依赖应用的自检，仍放在应用复制之后执行。
- runtime 中依赖文件及 `node_modules` COPY 放在 `dist` COPY 前；保留 builder 的“清单 / lock 在源码前”顺序，不把整个 context 提前 COPY。无需为了此次重排新建另一套 npm 依赖安装流程。
- 与应用版本有关的 LABEL 后置，避免仅应用身份改变使工具安装失效；AGENTS 保留靠后。保留必要编译和应用自检，不能以跳过检查换取快构建。
- 默认使用有效的本地 Docker 缓存，不使用 `--no-cache`、全局 prune 或每次强制刷新 base 的方式更新应用。不改变工具层输入时，不重复执行其安装；lock 真正变化时必须安装所需依赖，不能直接保留不兼容 node_modules。

**保证范围必须明确：** 在基础镜像、架构和安装输入一致且有效缓存保留的同机更新中，源码 / AGENTS 变更不应触发未变工具的联网安装，lock 不变时复用 npm ci 层。这不等于“每次构建都只运行一条 COPY”，编译、自检等本地步骤可以重跑。

**首次准备与后续更新分开：** 本次重排、已提交 timeout 变化、基础镜像变化、缓存被清理，都可能造成安装层重跑；只有 `docker load` 导入的最终镜像，也不等于具备 builder / web-assets 缓存。不能承诺任意旧机器首次升级完全零下载，但这不是下述用户澄清后的验收要求。

**用户进一步澄清（2026-10-20）：首次下载镜像耗时可以接受，重点是后续涉及 Worker 的更新，不要再次下载或安装整个工具环境。** 因此不再把“首次零下载”列为本轮必须解决的阻断；验收聚焦基础环境与依赖未变时，连续应用更新确实复用已有层。不自动从未知旧镜像做 overlay，不增加旧镜像兼容猜测或首次免下载专项机制。后文实施记录中“首次零下载不保证”是技术边界，不表示用户目标因此未满足。

- **镜像版本替换不等于全量传输或重装。** 每次仍可得到完整、不可变的新镜像；Docker 复用未变的内容层，只生成或下载缺少的层。粒度是层，不是层内逐文件 / 逐字节补丁，因此应用有变化时整个应用层可能重新传输，但不应带着稳定工具层重来。
- **当前 code-only 包路径：** `update.sh` 内部执行带缓存构建，首次建立有效缓存后，后续仅源码 / 指引变化复用工具安装层，lock 不变复用 npm ci；保留缓存、稳定基础镜像与安装输入。最终仍是新版完整镜像，不在运行中容器内用覆盖文件或 `docker commit` 热补丁。
- **以后若采用镜像仓库分发：** 发布端以稳定分层构建配套版本，安装端 pull 时复用本地已有的相同层，通常只下载变化的应用层；安装端不需要 builder 缓存，但发布端必须保持基础层内容稳定。完整 tar 的反复分发不等于网络增量下载。当前没有已确认仓库与发布授权，本澄清不新增 registry、上传或切换分发路径的实施任务。

### 9.3 推荐下一轮最小完整实现

目标是让旧用户在已有安装内通过一个明确入口升级，不必判断哪些服务、镜像或依赖需要手动补齐。

1. **先贯通现有三镜像准备。** 复用现有配置解析与更新锁；默认本地模式刷新 Worker、gateway、executor，executor 明确继承本次成功候选 Worker。失败不继续启动或迁移，不把 gateway 当 pi Worker 检查标签。自定义引用保留，明确检查存在性与实际更新范围，不自动覆盖用户镜像。
2. **再补源码一键入口。** 对普通 main 跟踪安装明确 fetch / fast-forward、依赖同步、正式前端、配套镜像及完整系统启动顺序；沿用项目现有脚本，不另造更新平台。停服务前先发现脏工作区、分支／远端不符或无法快进，不自动 stash / reset。新版本准备逻辑应加载拉取后的脚本，不依赖旧 shell 中已加载的函数。
3. **部署包入口继续保留，但禁止覆盖 Git 工作区。** 在停服务和替换之前拒绝目标 `.git` 目录与 worktree 文件，给出源码路径提示；非 Git 包安装继续使用新包的 `--target`。
4. **消除已确认的 executor 工具重装。** 在原有 Worker 工具层安排执行器真实需要的 `libnss3-tools`，executor 只追加服务代码。说明首次层输入变化会重建；不因此升级全部工具、换下载源或重做镜像体系。
5. **镜像发布单独定范围。** 一键拉取预构建镜像需要真实的仓库、版本及发布渠道。未确认发布目标之前不新增上传 workflow 或虚构下载地址；不把缺少预构建发布阻塞为源码一键入口的前提。后续发布应让三个镜像与应用版本配套，并持久复用构建缓存。

## 10. Docker Hub 配套发布与旧用户一键更新（2026-10-30，镜像数量安排已被第 12 节替代）

### 10.1 用户选择与本轮目标

用户同意采用 Docker Hub 作为后续镜像更新的分发渠道，可提供账号信息，并允许本机访问受阻时使用其提供的局域网代理。当前缺少的是 Docker Hub 用户／组织命名空间、三个仓库的公开／私有选择及可用登录，不需要收集账号密码或把 PAT 写进聊天、源码、日志、镜像和文档。

**推荐普通安装使用预构建镜像，源码构建继续保留给开发或自定义环境。** 发布端一次构建，使用端拉取缺失层；本地已有的相同工具层不重复下载。仍然是宿主应用＋三个执行镜像，不为“一键”强行改成全栈容器平台。

本轮目标是完整贯通：配套代码／应用包与三镜像发布 → 旧安装取得同一版本 → 保留配置和数据 → 准备成功后切换并启动完整系统。不只交付三个手动 docker pull 命令，也不只添加一个尚无真实产物的 workflow。

### 10.2 版本、发布与缓存

1. 建议使用三个仓库：`<namespace>/arena-worker`、`<namespace>/arena-traffic-gateway`、`<namespace>/arena-task-executor`；这是命名建议，不是现有公开地址。首次创建／上传前确认真实命名空间、仓库可见性和授权；可以先完成无需凭据的实现，不因缺少登录阻塞全部开发。
2. 使用同一实际 Git revision 命名、发布后不覆盖的版本标签关联应用和三镜像，并保留发布后的 digest；Docker tag 本身可被覆盖，因此不能只依赖三个会被分别覆盖的 latest。现有项目版本为 0.2.1，多次发布不能假定每次都已改变版本号。复用现有打包／版本信息承载这次实际需要的镜像引用，不另造发布服务或兼容框架。
3. GitHub Actions 在 main 更新后构建并发布配套候选，提供手动触发；不在 PR 或无写权限事件中发布。三个镜像成功且必要检查通过后才更新供安装器消费的稳定发布入口；失败不得让旧用户选择到半套版本。首次启用 CI 会产生真实构建和上传，用户需确认目标后配置 Secrets。若生成 GitHub Release 作为 code-only ZIP 下载入口，首次对外创建前明确版本和发布范围。
4. Executor 必须继承本次对应 Worker，而不是远端浮动旧 tag。沿用现有 Dockerfile，主 Worker 工具层置于应用层之前；将已存在于 executor 的 `libnss3-tools` 安排到稳定工具层，executor 只追加执行服务代码。它不是新增工具需求，不因此升级其他工具或重下载不变工具链。
5. CI runner 常是临时机器，应显式保留／恢复 BuildKit 构建缓存，避免每次从零安装。缓存策略只解决现有三镜像，不新增通用缓存平台。普通用户 pull 复用本地内容相同的层；发布端构建缓存和客户端镜像层复用是两件事，分别验证。首次安装、基础镜像／工具输入变化或缺缓存仍可能下载，不能承诺逐文件增量或永久零下载。
6. 先交付有实际可验证构建条件的架构，明确镜像支持平台；不以 Dockerfile 存在 arm64 分支宣称多架构已发布，不默认扩成多平台矩阵。禁止把宿主 runtime、私有 dispatch 配置、keyring、token、项目／漏洞原件或本地报告加入构建上下文或发布资产；沿用现有明确打包范围。

### 10.3 一键更新行为

- 实现第 9.3 节已确认缺口，但普通预构建模式改为取得配套镜像而不是本地重装工具。复用现有更新锁、安装和启动函数，提供用户可直接执行的一条入口；最终命令由实际实现确定，未实现前不把示例当作现有命令。
- 区分 Git 源码安装和非 Git 部署包安装：源码只在明确分支／远端且无受影响本地改动时快进；包安装从真实版本获取新包，并使用新版本更新代码。旧版本没有新入口时，文档提供一次性的引导取得方式，不能让旧用户执行不存在的命令。
- 显式管理官方发布镜像与用户自定义镜像的区别。新建官方安装可默认使用 Docker Hub；已有默认 local 安装须通过明确选项或一次迁移选择进入官方渠道，不能悄悄换掉用户自建镜像。明确选择官方渠道之后的日常升级不重复索要同一选择；自定义镜像继续保留，说明是否需要用户自行准备。
- 准备与验证三个版本配套镜像，必要资源下载尽量在停服务前完成；失败不继续启动半套环境或迁移数据库。网关不是 pi Worker，不套用 pi 标签检查。不得因某镜像拉取失败静默改为本地全量工具构建。
- 包更新器在停服务和替换前拒绝 `.git` 目录／worktree 文件；源码不自动 stash、reset、切分支或覆盖本地改动。拉取后使用新 helper，不复用旧 shell 已加载的更新函数。
- 保留 runtime、模型配置、完整 keyring、token、数据库及资料；沿用 PostgreSQL 迁移及明确的升级阻断。更新器不偷偷清库、删除历史容器、重跑任务或升级 PostgreSQL 大版本，也不宣称程序备份可以回滚数据库。

### 10.4 账号与网络边界

- 用户只需提供命名空间及可见性选择；本机通过正常 `docker login` 登录，CI 使用 GitHub Actions Secrets（例如 `DOCKERHUB_USERNAME`、`DOCKERHUB_TOKEN`）。PAT 仅授予所需仓库读写能力，不要求删除权限；不索要主账号密码，不回显已配置凭据。
- 用户提供的代理仅用于其本机访问受阻时的网络通路，不作为产品默认值或写入公开 workflow。新实施会话从用户提示词获得实际地址，先辨明代理支持的协议；不把连接失败自动解释为地域封锁，不使用非可信镜像源或关闭 TLS 校验。
- GitHub 托管 runner 通常不能访问用户局域网代理，默认使用 runner 的正常网络。宿主 Shell、Docker daemon 的 pull / push、BuildKit 构建内网络是不同配置范围，应只处理实际失败的一层。需修改 daemon 配置或重启 Docker 时先说明在途容器影响并征得同意，不能为了测试代理打断业务。

### 10.5 交付与验证边界

优先使用已有部署夹具验证三镜像准备、失败不切换、Git 目录保护、配置保留与参数语义；对真实发布检查三个镜像存在、版本一致及最小无业务执行检查。用同一基础输入的仅应用改动观察发布端缓存与使用端层复用，不清理用户缓存制造实验，也不创建新项目／调用模型证明安装。

首轮账号、可见性和发布范围明确后再实际上传；Git 提交／推送和首次 Release 创建按该实施会话的明确授权执行。缺凭据时应交付已完成代码和准确缺口，不能声称镜像已发布、一键升级已验收。最终分别报告实现、本地验证、镜像发布、用户实际安装升级，以及其他旧机器仍未知的部分。更新 README、主安装指南、CHANGELOG 与本方案，不另建同义交接文档。

## 11. 镜像数量纠偏：单一执行环境镜像的初步建议（2026-10-30，已被第 12 节替代）

用户进一步询问三个镜像是否重复、能否合并。**三个运行职责不要求三个镜像。** 第 10 节直接把当前构建产物数转为三个发布仓库的前提，增加了版本配套和安装负担，没有先评估能否合并；该取舍应纠正，不按现状直接实施三仓库发布。

### 当前代码事实

- 主 Worker 包含 pi runner、Node、Python、浏览器与研究工具；`container/Dockerfile:150–173` 复制应用、指引和字体。
- executor 的 `Dockerfile:1–9` 直接继承整个主 Worker，只增加 `libnss3-tools`、`server.py` 与启动入口。它并不是第二份独立下载的扫描工具全集：同一父镜像的相同层由 Docker 共享；但派生镜像随父镜像变化重跑附加安装，确有可删除的构建和发布负担。
- gateway 使用独立 Python 3.13 / Debian 基础环境，安装 mitmproxy、pproxy 和网络工具。它与 Kali Worker 的 Python／系统基础内容可能功能重复，但不同字节的层不能共享，不可据镜像虚拟大小相加推算真实磁盘浪费。
- 当前主 Worker、executor、collector 的容器启动、网络、挂载与运行身份分别由 `runtime/containers.py`、`runtime/traffic.py` 控制。executor 不携带模型凭据；collector 使用独立挂载并加入执行容器网络。保留这些运行职责不要求继续保留三个不同镜像。

### 推荐取舍与未验证项

发布一个包含现有运行能力的执行环境镜像，例如沿用 `<namespace>/arena-worker`，各容器按启动命令分别运行 Agent、执行服务或流量采集。Docker 在本机共享同一镜像内容，容器可写层仍独立；一个镜像不意味着把全部进程、凭据和权限塞进同一个容器，也不意味着把宿主 Server、Dispatcher、PostgreSQL 一并容器化。

收益是只维护一份执行镜像版本和一次拉取，消除 Worker／executor／gateway 配套遗漏；主工具依赖、采集依赖与应用代码保持合理分层，应用修改仍应复用未变依赖。代价是只需采集工具的容器也引用完整镜像，采集代码变化会发布统一镜像的新版本；这不等于每次运行会重复下载或把全部工具加载进内存。

这需要实际改造，不是把三个配置字段填写同一个现有 tag：必须将执行服务和采集代码纳入镜像，明确不同启动入口，核对统一环境中的 Python／mitmproxy／pproxy 与浏览器证书依赖，并贯通唯一镜像配置、旧配置处理、打包和部署检查。不能盲目跨 Debian / Kali 复制 Python site-packages，也不能未验证就承诺现有网关依赖无冲突。若发现具体兼容阻断，应比较局部依赖隔离与继续拆镜像的实际成本，不以泛化的“安全／微服务最佳实践”要求保留三镜像。

第 10 节关于 Docker Hub、版本与 digest、缓存、凭据、代理和数据保护的原则保留；三个仓库、三份版本配套及 executor 依赖远端 Worker 的发布安排不再作为推荐方案。本节仅为当时的初步建议，未修改生产实现、构建镜像或验证合并后的运行效果；进一步研究后的推荐以第 12 节为准。

## 12. 按实际研究用途收敛镜像与构建边界（2026-10-30，首轮本地实施完成，发布阶段待实施）

### 12.1 目标与结论

平台服务本地／内部自主安全研究，不是为了展示容器架构。保留浏览器、扫描器、脚本和自由 Shell 等实际研究能力，保证任务能停止、后台程序不会串入后续任务、证据有明确归属；同时减少安装等待、重复下载和用户维护配套版本的工作。本轮改善的是交付与执行环境维护，不声称镜像调整本身增强漏洞发现能力。

**推荐两个分发镜像：Worker 与 executor 共用研究环境镜像，网关／collector／网络 helper 继续共用独立采集镜像。** 不新增基础工具镜像仓库，不合并运行容器，不改宿主应用与 PostgreSQL 的部署形态。两镜像由安装／更新入口统一准备，不要求普通用户手工管理两组版本。

理由不是“三个太多、两个正好”：Worker 与 executor 已有相同工具依赖，后者只追加一项证书工具和执行脚本，没有足够的独立构建价值；gateway 的 Python 3.13、mitmproxy、pproxy 和系统网络依赖则形成真实独立的维护边界。保留它能避免将采集环境迁入 Kali 的额外适配，也让研究工具更新与采集更新互不触发构建。单镜像技术上可行，但本轮没有证据证明其运行收益值得承担依赖迁移与发布耦合；这不是长期禁止合并。

### 12.2 查证依据与性能边界（实施前快照）

- `container/task-executor/Dockerfile:1–9`：继承 Worker，安装 `libnss3-tools`，复制 `server.py`，设置入口。其 apt 层位于整个 Worker 之后，Worker 应用层变化就使这一步失去父层缓存；没有必要为这个入口维持第三个发布产物。
- `container/Dockerfile:25–31,58–173`：runner 编译已有独立阶段，扫描工具等依赖在应用 COPY 之前。字体当前追加在应用后；指导文档变化虽不会重装前面的扫描工具，仍会使后续字体缓存步骤失效。保持稳定依赖与频繁变动代码的边界，比镜像总数更直接影响构建成本。

### 12.3 最小改动范围与构建触发

1. **移除独立 executor 镜像产物，保留执行服务。** 将现有 `libnss3-tools` 纳入研究镜像应用代码之前的稳定工具层，复制执行服务；executor 创建时显式指定 Python 服务入口，主 Worker 保留现有启动方式。不要只把三个 tag 改成相同值。删除独立 executor Dockerfile／发布步骤及被替代的默认配置路径；贯通 `ContainerConfig`、traffic runtime、部署示例、打包与安装检查。旧标准配置做明确的一次转换；遇到不同的自定义 executor 配置不能静默丢弃，应说明需要的定向处理，不建立永久双配置 fallback。
2. **复用已有层，不重做工具链。** 保持工具版本、镜像源及运行能力；将稳定证书依赖、字体等放在频繁变动的 runner／执行服务／指引之前。仅为必要层序调整做一次构建，不把首次布局变化可能触发的重建说成零下载。runner 源码变化复用 npm 锁定依赖；不得默认 `--no-cache` 或 prune。基础镜像引用应记录并固定实际 digest，基础／工具升级另行显式触发，不让 Kali 的浮动 latest 在普通应用发布时悄悄扩大重建范围。
3. **按真实构建输入选择产物，而不是每次 main 更新重建全部镜像。** 对比拟发布 revision 与上次成功发布 revision 的相关输入，包括 Dockerfile、COPY 输入、构建脚本和基础引用；不只比较最新单个 commit。首次无对应产物才完整构建。被跳过的镜像沿用已发布 digest，而不是伪造本次构建成功。CI 显式持久化多阶段 BuildKit 缓存；最终镜像层不等于 builder 缓存。

### 12.4 一个产品版本，不强迫每个镜像每次都有新版本

复用 `deploy/package_release.py:195–212` 的发布 manifest，在配套发布时记录应用真实 revision、支持架构及两个实际镜像 digest；原 manifest 目前没有这些引用。应用版本更新可以继续引用上次不变的研究镜像或网关镜像，不再要求每次为所有镜像生成同 revision 的新构建。标签可用于查找，实际安装使用发布记录的精确产物；未准备完整的候选不成为稳定更新入口，不另建发布服务。

普通用户选择官方分发后，一条入口取得应用及所需镜像，只拉取缺失层；不因镜像数量为二而让用户手动选择配套版本。新包与镜像尽可能在停服务前准备好，失败不静默切回本地全量构建；按现有迁移规则切换应用并启动。沿用第 10.3 节的数据保留、Git 工作区保护和自定义镜像边界。代码推送不等于镜像发布，更不等于已安装实例自动升级；旧版本须有一次性引导路径。拉取新镜像不替换正在使用旧镜像的运行容器，不自动重跑任务；镜像引用参与容器复用签名，实施时明确新任务与已有项目何时使用新环境，不以重启应用冒称全部容器已升级。

1. **先整理当前累计代码。** 重新核对 status、分支、远端与 outgoing commits，保护所有已有修改。按业务依赖核对未跟踪源码是否必须纳入，特别是新增 schema／services 与前端引用；不能只 `git add -u` 漏掉生产依赖，也不能 `git add .` 带入根目录私有报告、runtime、凭据或本地测试材料。按既有方案与当前 diff 提炼 UI／ChatBot、会话与资料、执行控制、报告／流量、Token／价格估算、上传限制及 v76–v83 等实际用户可见变化；只记录源码证实的内容，不把旧实施声明当验收。
2. **补齐 CHANGELOG 和部署说明再提交。** 区分新增能力、API／schema 变化、升级阻断、实际验证与未知。旧记录可保留为历史，新条目必须纠正当前镜像数量、更新器能力和数据库版本。没有重新运行测试就明确说明；静态前端需与本次源码配套，必要时在发布构建中生成，不用现用 runtime/static 或未知构建目录代替源码产物。
3. **正常合入 main，不重写历史。** 在任务分支完成整理及提交；实施会话按用户本次 main 发布目标进行正常 push，先核对远端是否前进与分支保护。若非快进或受保护，按正常 merge／PR 处理，不 force push、不 rebase、不 reset、不覆盖其他提交；不要借同步 main 改写现有脏工作区。记录真实提交与推送后的远端 SHA。main 发布是源码快照交付，不自动等于稳定二进制发布或全业务验收。
4. **确定镜像来源后构建和上传。** 建议两个仓库为 `docker.io/<已确认namespace>/arena-worker`、`docker.io/<已确认namespace>/arena-traffic-gateway`，这不是已存在的地址。用实际发布提交的不可混入私有运行资料的构建输入，保留有效缓存和稳定工具层；不上传整套本地候选标签，不直接把未知来历的 local 镜像标为最新版。无输入变化且可证实来源的镜像可以复用，不能凭固定 pi 标签推断源码一致。
5. **首批只承诺实测架构。** 使用基于真实 Git revision 的版本 tag，记录远端 digest 和实际 platform；不覆盖已发布版本标签，不把本地 Image ID 当 registry digest，不默认承诺 arm64。研究与采集均准备并检查成功后才对外称配套完成；失败的半套不更新稳定发布入口。本轮不强制提供 `latest`，更不让用户只依赖可变的 latest 配套。

“整理镜像”在本轮指收敛发行产物与版本身份，不是清理本机磁盘。旧 executor、候选、缓存和容器都不删除；若用户另外要求清理，再核对引用和回退需要，不能全局 prune。

### 13.4 旧安装怎样更新，以及这次必须说清的限制

- **Git 源码安装：** 先识别真实安装目录、远端、分支和本地修改；main 且可正常快进的安装按指南取得目标代码，再同步依赖、正式前端和配套两镜像，最后在获准维护窗口重启。运行与调度确已静止、备份及必要迁移条件满足后才切换；单独 pull 源码或单独 pull 镜像均不构成完整升级。不用 ZIP 覆盖 Git 工作区，不自动 stash／reset／丢弃用户修改。

- **包更新器缺少 Git 目录硬保护。** 当前 `deploy/update.sh` 没有 `.git` 目录／worktree 文件拒绝分支，不能把指南中的“不用于 Git 工作区”说成脚本已有保护。发布实施可在停服务、暂存替换之前补最小的明确拒绝，避免普通用户误用 `--target` 覆盖已有源码修改；不自动 stash、切分支或修复工作区。
- **从旧 local 改用 Hub 必须是显式选择。** 保留用户自定义镜像与运行限制；不悄悄覆盖定制 executor 或把远端拉取失败回退成本地全量下载。旧 `task_executor_image` 的标准值已有一次转换，自定义值按当前明确错误处理，不能一律删字段蒙混升级。
- **旧聊天是这次具体升级缺口。** v76 可阻断没有对应消息的 chat run；迁移成功后有旧文件标记或未知 session 的会话仍可能返回 `conversation_file_migration_required`／`session_verification_required`。有这类数据的安装不能被告知“运行 update 即全部无损可续聊”。新版资料库 v82 还会读取原资料正文与知识目录，必须保留并正确加载原安装的外置路径，不能只复制数据库到空目录做升级。
- **必要补齐仅限现有迁移入口的直接运维调用。** 发布实施会话核实旧数据升级步骤；若要交付“有历史聊天也可按文档升级”的完整路径，给既有文件／session 迁移函数提供一个局部、可明确调用的运维入口及顺序说明。使用托管事务、原 Dispatcher 身份和原机器挂载；没有归属、原件或 SDK 证据时只保留受影响会话的明确阻断，不猜目录、不假解锁、不建兼容 fallback、不自动启动或停止历史容器。若本轮不实现该入口，须将有此类数据的安装列为尚未覆盖的升级情况，不能宣称所有旧版均可直接升级或以本机早已迁移代替交付。
- **数据与回退：** PostgreSQL、资料正文、Artifact、会话材料、runtime 配置、完整 keyring 历史版本、机器 token 与外置目录要匹配保留。升级前按实例安排一致备份；程序临时备份不等于数据库或整套环境回滚。迁移失败不删数据、不修改旧 checksum，也不自动恢复／重跑任务。更新 tag 不替换已有容器，旧容器的保留与后续使用按实际生命周期处理。

发布实施默认不升级当前正在使用的实例，也不访问其他安装机器。源代码推送、镜像上传、ZIP 上传和旧机器升级分别报告结果，不相互替代。

### 13.5 Docker Hub 所需信息与凭据边界

需要用户补充的不是邮箱密码，而是：

1. Docker ID 或组织 namespace，及是否拥有这两个仓库的推送权限；邮箱不是镜像仓库 namespace，不能从邮箱猜用户名。
