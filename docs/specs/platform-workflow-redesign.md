## 2. 已确认问题与证据边界

### 2.1 本轮实际观察

- 2026-11-01 核实实际 Server 进程工作目录为本仓库、监听 `8001`；进程配置的静态目录为 `runtime/static`，不是源码构建输出目录。源码构建成功不能代替发布生效。
- 正常登录后查看项目列表、现有项目运行列表与一条已有运行日志，相关项目、runtime、task-runs 请求返回 200；日志正文可以读取。不复制日志、目标信息或账户数据到方案。
- 登录前 `/auth/session` 的 401 是未登录检查，不是运行读取故障。当前没有捕获用户所述间歇错误的当次失败请求，不能将下面的源码问题断言为所有历史报错的根因。
- 只读检查有限的近期 Server／Dispatcher 日志尾部，未见 traceback；这不证明更早没有失败或实际任务成功。
- 浏览器使用 1920×1080 CSS 像素等效桌面视口、应用根缩放 0.9；本次未对含敏感原始正文的页面留截图，尚非改动后的视觉验收。

### 2.2 可达的局部失败放大路径（R1 依据）

1. `cairn/frontend/src/features/runs/useRunsPage.ts` 的 `loadRunDetails` 使用 `Promise.all` 同时读取 command-events 和 artifacts，并在两者都成功后才写入任一结果。命令审计读取失败会让已成功的资产列表与日志入口一起无法更新；反向同理。不是两份结果必须原子接受的业务事务，而是两个独立只读区域。
2. 同文件 `loadTerminalOutput` 虽有 `preservePreview`，但 catch 仍清空 `terminalPreview` 与 `terminalPreviewSource`。同一日志一次后台刷新失败，就会丢掉用户已经看到的正文。
3. `RunsPage.vue` 的日志错误分支在正文分支之前，单纯保留缓存并不能解决正文被错误面板替换的问题；请求层和展示层必须一起改。
4. 命令／资产区域只用数组为空判定“本轮没有调用／没有写入”。初次请求未完成或失败也可能出现同样的空数组，容易把“尚未读到”写成业务事实。
5. 当前已经有项目／运行／产物身份检查与请求代次保护。它们防止切换后混入旧内容，有真实用途，应保留或等价简化，不能为了保留正文而跨身份显示缓存。

上述触发条件是正常使用中可出现的单接口读取失败，发生频率尚未知。对应最小结构变化是按读取来源划分加载与错误边界；不需要新增后端聚合 API、全局容错框架或永久并行实现。

### 2.3 上轮静态分析结论如何使用

- 项目默认进入图谱、项目 Agent 跳全局、材料入口割裂，是产品路径取舍，不等于对应 API 已经坏掉。
- 项目元数据的“已暂停”和物理执行清理是不同事实。`projectRuntime.ts` 普通动作目前主要按元数据给入口；服务端仍做锁内校验。**旧方案曾明确选择这种呈现，不能谎称是实施遗漏。** 新设计若改变该取舍，需同步直接消费者，而非新增一套持久化项目状态。
- canonical 漏洞、各次 Observation、复核、人工处置和正式报告接受各有语义；当前入口可能令用户混读，但不能自动将历史确认改成最新否定，也不能把人工“已修复”当作复核证明。
- 总报告的终态约束与单项报告不同，平台已有单项交付；不以“完全不能中途交付”作为重构依据。
- runner 有 usage，聊天另有用量记录；缺的是用户能解释的项目成本视图，不能断言所有原始计量都被丢弃，更不能把 SDK cost=0 当作免费。
- 周期计划建立新项目，不自动等于持续工作成果比较。是否需要新的长期对象须从真实跨轮使用路径论证，不能先增表后找用途。

这些方向需要各轮补足定向证据，R1 不顺带实现。

## 3. 从使用结果推导的目标设计（重新建立，尚未实施）

本节替代此前以现有对象和阅读入口为起点的推荐设计。目标是非攻击性的事实管理、人工审阅与可靠交付；不据此声称覆盖整体渗透能力。以下是目标行为与职责，不是要求逐条新建表、服务、状态或审批步骤。

### 3.1 先定义应得到什么，不先决定叫什么模块

使用者应当能够交代工作背景和交付需要、保留材料，随后直接判断：已经得到哪些可信内容、依据适用于什么条件、哪些问题仍未知、哪份结果可以交付、为此消耗了多少已记录资源。回答不应要求使用者拼接内部阶段、日志、文件名与多个状态标签。

由此推导四项基本责任：

1. **事实可追溯。** 一份材料的原件、所属上下文、来源和版本可以明确定位；后来的解释不能悄悄改写原件。
2. **主张与依据分离。** 人工处置、观察事实、解释和审阅结论分别表达。支持、反证、条件不同与尚未验证不能被一个最新标签抹平。
3. **交付有明确范围。** 接收者可以知道成品包含什么、依据哪个时间点的材料、遗漏或未解决什么；不是看到一个文件就猜测它是否代表最终结论。
4. **投入可解释。** 已记录消耗有归属和来源，未记录范围明确；有计价依据才给出金额，不能把不完整计量包装成精确账单。

这些责任由谁承担，再决定接口、存储与界面。现有Project、TaskRun、Observation或Artifact是否适合承载，是随后要比较的实现选项，不是设计前提。

### 3.2 事实与材料：保存成功不等于结论接受

目标行为是：已经成功保存的原始材料，可以独立于解释、审阅或报告生成结果找回；无法读取和根本没有材料可以区分。后续步骤失败不能把已保存材料变成不存在，也不能把保存成功升级为结论成立。

保存方负责原件与来源关联的真实性；解释与审阅方引用明确的材料版本；读取方只呈现所获事实和读取结果，不替生产者补造缺失来源。若当前链路没有记录必要关联，需修正真实的写入与持久化责任，不能只增加一个空的来源面板。

这不预设另建证据平台或复制原件库，也不设计自动继续攻击或重跑机制。实际改造前需查明已有存储与关联能否满足以上行为，再决定复用还是替换。

### 3.3 人工审阅：让分歧可判断，而不是堆更多状态

目标行为是：同一事项的不同观察可以按各自材料和条件被审阅；新的不支持记录不自动抹去此前在不同条件下成立的记录，人工标记也不自动成为事实证明。使用者不必靠多次切页手工猜测哪些内容属于同一次观察。

审阅结果引用明确对象与依据，保留未决分歧；原文继续可达。只读汇总可以帮助理解，但不能成为另一套权威事实或替代原始材料。是否新增关联或调整原有模型，取决于当前模型能否直接表达这些关系；不默认用更多Badge、统一置信分或模型摘要解决所有权问题。

### 3.4 可靠交付：先有交付范围，再有排版与下载

目标行为是：一份正式交付对应明确的内容范围、所引材料版本及真实的接受结果；后来的观察不能静默改变已经交付的事实。材料尚未审阅、存在缺口或生成失败应保留其真实含义，不用“任务完成”代替“成果可交付”。

交付范围的确定、成品生成和接受记录是不同责任，不必对应三个新服务。需要保留的是它们的实际因果关系：选入的材料能追溯，排除或未决项能解释，生成失败不损坏原件，文件存在不冒充正式接受。具体是否需要调整接受模型、生成接口或版本关系，留待读取真实链路后决定；本节不是新增流程或强制人工审批的依据。

### 3.5 计量：先把消耗记对，再决定如何展示

目标行为是：使用者查看某项工作的投入时，能区分已记录部分、未记录部分和有依据的金额估算。记录应归属实际产生消耗的对象，汇总不能重复计入同一来源，也不能因最终失败就遗漏已发生的消耗。

计量采集、持久化、归属和展示必须接得上；仅把现有usage字段铺到页面不是目标完成。需要核实计量事实从哪里产生、哪些环节缺失以及历史能否追溯；缺失历史不回填猜测值。现有记录足够就复用，缺口在产生端就处理该缺口，不先建设通用计费平台，也不把费用展示升级为自主任务分配或攻击预算优化。

2026-11-04 已核实项目网关丢失结构化用量、直接试用／诊断未统一记录及零价占位；本次按第 5F 节贯通全入口消费、持久化、估算和工作台，而不是重复 R4 的只读字段投影。

### 3.6 读取与界面：是上述责任的使用入口，不是替代品

读取故障保持局部，已获得的同身份材料仍可阅读，并说明是否过时；未知、读取失败和成功为空分别表达。页面不能根据读取失败改变业务结果或自动触发执行。

主界面按使用者当前需要判断的事项组织，不预先规定必须用图谱、漏洞列表或某个旧页面作首页。布局选择应在目标事实与动作明确后确定；不能先搬入口，再倒推新架构。R1–R4中已经满足目标的行为可保留，不因重新设计而重复返工。

### 3.7 工程选择、迁移与直接验收

目标行为确定后，定向核对其相关生产者、持久化、接口和实际消费者。对每个已证实差距，选择复用、删除冲突或替换机制，并说明改变了什么行为；不为显得彻底而换语言、引擎或引入通用平台。需要替换的接口应贯通直接消费者，保护现有材料，删除被替代路径，不永久维护双份事实或静默fallback。

每轮用一个最直接的行为案例验收，例如：读取某一路径失败而其余材料仍可读；同一事项的冲突依据没有被覆盖；已交付材料的引用仍对应原版本；已记录消耗没有被重复汇总。案例按实际改动选择，不把这些例子自动变成一整套测试，更不以模拟案例证明真实业务已覆盖。

已按此基线查证聊天计量丢失路径并完成R5代码与维护，另查明人工处置缺少操作者、理由与来源历史，按5E完成R6实现、隔离验证及正式部署，具体边界见6.14；其他目标机制仍需分别核对，不能把方向性设想全部列为已实现。R5真实新消息计量链、R6正式样本交互尚未验收，不承诺整体新架构已经落地。不会把自主攻击选路、漏洞利用、目标访问或攻防编排改造交给下一实施模型。

## 5D. R5：聊天已记录计量不被后续未知抹除（2026-11-01，实施中）

### 目标行为与已确认缺口

目标先于现有结构：一轮中已报告的消耗应保留为可追溯小计，后续响应缺少计量或最终失败不抹掉它；同时不能把有缺口的小计冒充总量或金额账单。只解决聊天计量，不优化攻击投入、调度、执行或恢复。

监督已独立核对实施会话交回的路径：`container/pi-agent/src/runner.ts` 的 `message_end` 计量在任一非aborted响应无usage或分量和不为正时将 `usageKnown` 置false，结束时仅 `usageSeen && usageKnown` 才输出usage。故“先报告正数、后未报告计量”的正常多响应序列会把前面的累计也变成null；`dispatcher/tasks/agent_chat.py` 转发、`server/services/agent_conversations.py:finish_turn` 保存的就是这个null。这是源码可达路径，未复现真实历史个案，发生频率未知。没有已证实的重复计入或错误项目归属案例，不据此扩展改造。

### 实施契约与必要上下游

1. 聊天计量保留已有正数部分的累计；完全没有可核验计量仍为null。SDK缺失分量也填0，因此保留当前分量的正数／null处理，不把未知改为0，不把一次最终失败当成此前没有消耗。只处理当前已纳入计量的非aborted响应，不扩大到取消／超时回收或其他未核实路径。
2. 为区分“本轮明确缺计量”和“历史没有这项记录”，使用一个聊天专属的 `usage_missing_responses: int | null` 元数据：新聊天记录当前计量范围内无可用usage的响应数，历史／未产生该信息为null。0仅表示没有观察到此类缺失，不证明所有分量完整，也不证明账单完整。保持usage四分量原结构，不新增金额、总tokens或第二份权威计量。
3. 计量采集与累计可提取为一个小型纯函数／模块供直接验证，但不另造通用meter框架。非聊天信封保持原有字段集合与计量行为；新增字段仅随chat结果输出，不顺手扩展共享结果网关或非聊天严格协议。
4. 直接贯通聊天结果校验、公开正文被拒后的失败回执、Finish输入、同一TaskRun的JSON保存、终态相同回执比较及公共消息投影。新增计数只接受非负整数或null，不接受bool／字符串猜测转换。重复相同回执仍是原值比较而非加算；不同计量元数据仍应判冲突。已有历史缺字段与新记录有具体计数按真实情况表达，不回填历史、不迁移数据库。
5. API与原用量展开区读取该元数据，有缺失时明确仅为已记录小计；历史未知不伪装成“计量完整”。保持同会话同TaskRun归属、正文／凭据输出边界、已有金额未知与关联任务不包含的范围说明。不新增页面、图表或常驻说明墙。

### 目标与已核实差距

### 完整行为与取舍

1. 保留既有漏洞当前状态作为唯一当前状态事实，不增设另一套“审阅状态机”或审批队列。将人工状态操作改为一次明确提交：状态、可选说明、当前选定的发现（或独立人工记录）与当前记录版本。说明未填写就如实为空，不编造理由；不强迫填写长评审表。
2. 服务在原有项目写锁与同一事务中校验对象、版本并同时保存新状态和不可覆写的人工处置记录。操作者来自真实登录身份，不能由客户端自报；新记录包含前后状态、时间、原样说明与依据关联。错误对象、跨项目发现或读取后已变化的记录明确拒绝，不能悄悄换成最新发现。正常多标签页或机器更新后提交会遇到版本变化，这是具体可达场景，不增建通用并发框架。
3. 新增一张职责单一的人工处置记录表是为保存此前没有的历史事实，而不是复制当前状态供另一套决策消费。Observation已有不可变来源，优先引用它及其材料身份；人工记录中可编辑的依据须保留处置时版本。只保存必要的引用、原有材料结构／摘要身份，不复制二进制原件或新建证据库；不要声称用户逐项读过提交时所有材料。处置历史不参与自主工作选路、调度、自动复核或漏洞确认算法。
4. 直接调整现有PATCH消费者，不为旧项目回填不存在的处置历史，不保留旧的匿名状态写入口。非状态的既有机器材料更新保持职责不变；人工处置必须归属实际用户，不能把机器调用伪记成人。API精确条件校验，不批量更改现有权限体系。
5. 详情里的操作表单和历史读取贯通新写入。显示每次决定的真实操作者、时间、理由与当时选定来源，能够回到该来源；当前处置与独立复核仍分开。后续处置只追加，不覆盖前一条。若最新自动结果改变当前状态，不把某条旧人工记录伪称为当前状态的原因。

### 5F.2 一个消费来源，独立于业务对象寿命

在当前 PostgreSQL 增加职责单一的消费记录，覆盖共享 runner 和两类直接推理入口。新增的原因是现有 TaskRun 会被级联删除、直接试用／诊断没有可靠 TaskRun、业务终态与已发生消费不同；不是建设支付账务平台。不得用前端 localStorage、日志正则、当前存活项目的 runtime_context 遍历求和替代权威持久化。

最少记录以下事实；具体表／字段名按当前代码风格确定，不预建通用事件平台：

- **归属与来源：**认证决定的 tenant 或平台诊断 scope、source、实际项目／会话／直接请求关联及执行 owner。聊天 project_id 仅为上下文，不能据此自动把聊天费用计入该项目。派生报告／复测／项目的消费在自己的执行上记录一次，不同时加到父聊天。
- **唯一消费身份：**业务归属＋TaskRun／直接请求 ID＋runner invocation／实际请求尝试＋响应序号或稳定响应 ID。不能假定裸 TaskRun ID 或会话 ID 就足够。相同回执重送只确认原记录，真正再次发出并得到计量的响应独立记录；同一响应的累计 usage 更新不是新的消费。
- **当次模型快照：**保存可解释消费的模型配置身份、版本、协议及必要显示名；不依赖活模型 INNER JOIN，不保存密钥、请求正文、自定义认证头或完整运行环境。服务端验证执行绑定与认证 owner，不能信任客户端自行提交 tenant／价格。
- **时间与量：**真实可获得的响应发生时间、首次接收时间、标准化四分量及各项已知性、计量来源和完整性。明确缺失不能补零；取消／失败已有正数也保留。没有拿到 usage 的实际请求保留未知／中断事实，不推算 token。
- **计价依据：**有效费率快照、币种、已知部分估算金额及未计价原因；同一记录不随当前模型编辑被静默重算。数值采用 PostgreSQL 精确数值与服务端 Decimal，API 金额用十进制字符串，不用 JS 浮点负责账本计算。

消费记录不设置随项目／会话／模型删除的 CASCADE；已删除对象仅失去跳转，不失去历史归属和数值。暂不设计租户销户／财务留存平台。查询索引服务 tenant＋时间和真实来源聚合即可，不增加缓存服务、物化账单流水或第二套状态机。

### 5F.3 采集、失败留存与幂等交付

1. **采集提前。** 在共享 runner 的实际响应边界取得 usage，先于候选校验、公开正文接收和最终业务结果判定留存；所有调用用途使用同一标准化逻辑，不只聊天保小计。aborted／error 响应若已有 usage 必须保留，不能因 stopReason 丢掉；尚未获得的部分仍未知。
2. **不押注最终 stdout。** 已获得的消费事件按现有可复用的持久回执／受控 spool 范式留存，由 Dispatcher 以原机器身份提交；Server 接受后标记交付。失败、取消、超时以及正常回收路径都要接到已有记录的交付／重放，不为了获取用量重新运行模型。未获确认的记录不能因正常容器清理被静默删除；优先复用现有宿主持久挂载与恢复周期，不新增消息总线、守护服务或通用重试框架。原始业务材料和消费回执分工清楚，不把候选提交成功作为消费接受条件。
3. **控制到可证明范围。** 收到的响应记录可幂等重送；硬终止之前从未暴露 usage 的部分无法保证恢复，不能写“绝不漏计”。对于可观察的请求开始／中断保留缺口；SDK 内部重试未暴露的计量明确未知，不给每个流 token 编造独立调用。实际请求身份与底层可用接口在实施前定向核对，不修改 `node_modules` 或升级依赖来绕过问题。
4. **现有消息读写收敛。** 新聊天、TaskRun／消息用量与工作台读同一消费来源。旧 runtime_context 中的历史原始信息保留，不再让新完成回执独立维护一份可漂移累计；消息 API 仍按原归属验证访问。不能把消息投影与消费账本再相加。
5. **直接 HTTP 边界补齐。** `/models/test` 和有实际推理的管理员 connectivity test 直接接统一记录／计价服务；HTTP 返回失败但含可信 usage 仍保存，没 usage 不当零。草稿按实际协议／模型和操作者归属记录，不擅自借已保存 model_id 的费率；不匹配时金额未定价，不阻止试用。平台诊断独立 scope，无价格时如实未定价。
6. **会话／项目执行本身不改。** 不改工具、研究选路、Prompt、阶段或生命周期；计量持久化失败不能被伪装成任务成功／零消费，也不默认取消已经在做的研究。优先持久重送并将计量缺口显式呈现，复用已有错误处理，不制造新的全局停机门槛。

### 5F.4 Token 与费用的明确口径

**Token：**标准化后，`input_tokens` 表示非缓存输入；缓存读取／写入独立于该输入，`output_tokens` 包含协议已纳入输出的 reasoning。只有确认这四类互斥且已知时，完整合计才是四者之和；存在缺项时给已记录小计与缺失范围，不将 null 补 0 后声称完整。

- OpenAI 原始 prompt／input 常已含缓存，须在协议边界转换一次；pi SDK 当前标准化 input 已扣缓存，不能再扣或再把原始 input 与缓存重复相加。
- Anthropic 初始与后续流 usage 是同一响应的累计更新，按字段语义合并为终值，不能把每个 delta 都加一遍。
- completion 已含 reasoning 时不再加 reasoning；工具循环、修复／续写重新发送上下文产生的输入则是真实新消耗，不能按文本相同去重。
- 显式上游零值与 SDK 为缺字段填的零不同。能取得原始 usage 的入口保留字段存在性及协议意义；只能取得 SDK 丢失了存在性的结果时标注其限制，不能以 `missing=0` 声称完整。定向查证当次运行 SDK 接口，修复可取得但被本平台丢掉的信息，不长期用未知掩盖本轮可修缺口。

**价格与金额：**在现有模型配置表单／API 增加一个紧凑“计价”分组：币种、每百万 Token 的非缓存输入／输出／缓存读／缓存写单价。字段可留空，空白表示未定价，显式 0 表示配置为零；非负有限十进制，不强迫为使用模型填写价格。服务端持有规范计算逻辑；费率依据随本次执行／直接请求的真实模型绑定冻结，新配置用于后续绑定，不重算已确定的历史费用。不自动联网抓价格、不按模型名字硬编码官方价格，也不把 SDK 当前零 cost 当依据。

可计算部分的费用为 `Σ(该类 Token × 该类每百万单价 / 1_000_000)`；任一实际消费分项缺 usage／费率时，只能称已计价部分。未知费率但已明确数量为 0 的分项不制造虚假费用；未知数量不能套该例外。缓存时长／服务层级等影响计价、却没有足够字段或匹配费率依据时，明确未定价范围，不猜一个默认倍率。不为潜在供应商差异先实现通用价格规则引擎。

不同币种分别汇总，不猜汇率；低于显示精度但大于零的金额不要显示为免费。费用始终叫“估算费用”或“已计价小计”，不写已扣费／供应商实收。本轮不设置真实单价，实际费率由用户按自己的供应渠道在既有配置页填写；无真实费率仍可完成实现和受控计价验证，但不能宣称现场金额已验证。

### 5F.5 汇总、权限、时间与历史范围

- **统一查询来源：**扩展现有 `GET /overview`，保留项目／漏洞输出，增加消费汇总对象：总计、今日、最近 14 个自然日每日数据、同 14 天的模型汇总、统计范围／时区／区间和覆盖信息。命名最终以同步后的 schema 为准。总计是该范围的全部已记录消费，不是仍存在项目的总和，不只算成功任务，也不排除复测／报告／模型试用。
- **权限：**沿用 overview 的普通用户租户聚合、超级管理员全局视角。租户聚合只提供 Token／费用／模型汇总，不泄漏其他人的聊天正文、标题、会话 ID 或个人调用明细；聊天单条详情仍本人可读。超级管理员可见平台诊断独立来源，普通租户不能看到平台诊断或其他租户数据；不接受任意 tenant 参数跨界。
- **时间：**服务器以一个明确配置的 IANA 业务时区定义“今日”和每日桶；复用已有平台时区（如果存在），没有则采用明确配置项、默认 UTC，不猜部署机器本地时区或由每个浏览器各算一天。响应返回时区、生成时间及 `[start,end)` UTC 区间，UI 可短显“今日 · UTC”等真实范围。使用服务器当前时刻，正确处理跨日／DST；总量不随时区变化。响应发生时间可核实时按其归桶，只有首次接收时间时按首次接收并标注依据，回执重送不移动日期。
- **完整性：**分别表达已记录 Token、未知／部分计量请求、按币种已计价金额、未定价范围以及计量启用时间；不能用一个“完整”布尔把它们混为一谈，也不把相互重叠的缺口数量加成总调用数。已采集到的零消费日可为零，计量启用前／未知覆盖期不是零。
- **历史：**本轮不全盘扫描 stdout、不承诺恢复全历史。对现存聊天结构化 usage，在新消费迁移时按原同会话／TaskRun 身份幂等导入为明确的历史汇总粒度，保留原缺失信息；没有已知当时费率则不按今天价格补算，无法确认发生日时不造日趋势。旧 usage 原件保留，新读取转为统一消费来源。缺少 usage 的历史保持未记录，不为其制造逐响应行；项目 Artifact 是否值得定向回填属于后续明确范围，不为补图重跑模型。历史导入与新逐响应记录不得同时累计同一 TaskRun；用明确启用边界／执行标识排除重叠，不长期运行两套 fallback 汇总。
- **迁移与在途：**只做当前 PostgreSQL。实施前核对最新迁移编号、在途旧 runner／待发完成回执和原读取依赖，确定单次切换边界；旧回执能被保全但不能与新消费重复计数。不能为方便切换清理用户队列／会话或静默替换正在运行的容器。没有安全切换条件时交回确切加载阻塞，不宣称完整生效。

首页仍是只读轻量查询，不调用模型、过期维护或项目详情组装；按租户／日期索引聚合，不为每条消息逐一查询。既有“固定四次 SELECT”是旧接口实现描述，不应阻止本次新增有限聚合；也不能扩大为每次首页扫描全部原件。
