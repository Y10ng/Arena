## 1. 用户目标与参考依据

用户希望借鉴 Cyber 的新建入口：通过弹窗选择场景、填写任务信息、添加文件／资料，并支持计划任务。不是照搬外观或完整系统，而是结合 Arena 的实际能力实现；本分析会话负责方案与提示词，用户另开会话实施。

2026-10-13 用户明确调整：以功能落地为主，减少冗余测试、重复验证与机械分轮。此次剩余目标包含场景引导、单次定时和每日／每周重复运行；这些是一个实施任务的内部步骤，不要求每步返回分析会话。A 的真实付费研究验收不是继续开发的前置条件；上下文确实不足时才在可用节点记录交接，不把未做的计划任务宣称完成。

### 1.2 推荐方向

**以一个“新建项目”弹窗承载准备工作；保留开放的 Origin／Goal，复用已有资料消费链与场景目录，增强可编辑的输入引导；计划启动单独打通持久化执行链。**

收益是减少跳页、减少反复填写、让输入真正参与执行，并使“何时开始”可理解、可控制。本方案不据此宣称已提升漏洞发现质量；场景标签、资料上传成功和启动成功都不是发现效果证明。

不照搬以下内容：

- 不把内部平台改造成按套餐分级的公网 SaaS，不增加协议弹窗、逐次审批或租户治理工程。
- 不要求先填固定格式 URL，不把背景文字或附件内的地址自动扩成授权范围。
- 不恢复固定 Explore 次数、复核预留、Coverage 必经流程或强制无限期授权确认。
- 不用“场景”硬编码侦察、扫描、利用、复核等固定步骤，也不新增角色专属 Agent 组织。
- 不将未来尚未接通的功能先做成可点击按钮，不交付只保存 Cron 文本却不会执行的计划。

### 2.2 契约与确定性边界

- 创建 schema 使用 `extra="forbid"`，已支持 `scenario`、`resource_batch_id`、`library_keys`，但没有 `create_disabled`、`start_at`、Cron 或初始状态参数。不能因为现行协议文档的示例没有列出 `scenario` 就将它删除，也不能仅在前端添加调度字段。
- `authorization_expires_at` 必须显式发送未来绝对时间或 `null`，留空无需另勾选确认。`explore_deadline` 是停止时间，非启动时间；两者独立。与 `docs/specs/server-protocol.md:244-250` 一致。
- 当前统一使用 goal-driven 执行主线，不从场景恢复固定 Explore 次数、复核预留或固定阶段。依据：`cairn/src/cairn/server/services/assessment_policy.py:77-143`。
- **创建默认会进入执行调度，没有“仅创建”或“创建后启动”开关。**首轮必须明确告诉用户这一行为，不能暗中改成草稿，也不能声称已支持延迟启动。
- **前端 busy 与 batch 单次消费不等于请求幂等。**已检查创建入口未见创建幂等键／请求去重；成功响应丢失后，无法保证重发返回原项目。批次已消费时也不能以重传全部文件来猜测恢复。依据：创建 schema／route／service，以及 `cairn/src/cairn/server/services/project_resources.py:713-799`。
- 当前显式取消调用 batch 取消，组件卸载只移除键盘事件；弹窗关闭需要贯通取消与关闭保护，不能只卸载组件。依据：`NewProject.vue:714-737`。
- **已知授权语义缺口，不能被表单美化掩盖：**创建服务会从 Origin 提取 seed targets，授权集合包含 seed／approved。依据：`cairn/src/cairn/server/services/project_records.py:744-791`、`services/targets.py:37-63`、`cairn/src/cairn/project_authorization_contract.py:115-126`。即使发送 `targets=[]`，当前 helper 仍会从 Origin 补入 seed。因此“不把背景地址自动视为授权”是长期要求，不是现状。A 未修复；内置模板不得加入示例地址；本次计划创建明确按第 6.5 节收敛为用户选定的显式 targets，不重写历史授权或扩成全仓授权改造。

### 2.3 本轮没有做的验证

没有运行 Arena、创建测试项目、访问被测目标、调用模型、执行测试套件、读取业务数据库、修改数据库或构建部署。部署实例的实际场景目录、Worker 能力与模型读取效果未验证。参考站仅确认前端交互；定时器与研究效果均不冒称已验收。

具体字段顺序可按现有组件微调，但不能为复刻截图删除必要的项目名称、现有场景或 Worker 设置。**2026-10-19 取舍更新：项目组不再是必要字段，应按重设方案第 15.14 节连同分类关系一起移除；不是保留隐藏默认组。**场景区先显示当前选项，可展开切换已有目录；Worker 区折叠时仍显示选择摘要，缺少必需资源时自动展开并说明原因。第一轮没有定时／周期功能，不显示占位卡片、灰色假按钮或“即将上线”的复杂区域。

### 3.2 权威来源

| 信息 | 权威来源与设计边界 |
| --- | --- |
| 背景与目标 | 沿用 Origin／Goal；场景不得再保存一份覆盖它们的隐藏最终指令 |
| 授权与执行边界 | 沿用当前授权、项目配置及相关校验；场景、文件和时间配置不能代替或扩大授权 |
| 上传资料 | 原始资料和已有版本／关联记录；显示名、摘要、索引不是原件的替代品 |
| 场景及输入建议 | 复用现有 scenario catalog、运行配置引用及 Origin／Goal 模板，不另建前端场景目录；用户编辑后的正文是本次目标输入，场景运行配置仍按现有链路消费 |

| 周期计划 | 每轮生成项目的配置与触发记录；每次项目保留独立事实、证据、消耗和执行历史 |

不为了全字段齐全建立“项目草稿平台”、第二套资料模型、通用工作流引擎或前后端各一份执行策略。

## 4. A 已实施基线：弹窗与现有资料流程

本节保留当时范围及取舍，不是要求本次重做。下文“首轮／本轮”仅指 A；有关创建未知状态与幂等的后续决定以第 6.4 节为准，验证以第 8 节为准。

### 4.1 完整范围

第一轮交付“在项目列表打开弹窗 → 填写当前已有字段 → 选择本地文件／已有资料 → 按现有创建与启动语义完成操作 → 进入项目”的最小完整路径。

先搬迁／复用当前表单及提交流程，再在相同流程中整理资料入口与状态。不能在旧创建页、弹窗和项目详情各复制一套创建逻辑。现有路由若仍有调用方，改为进入同一弹窗入口；是否保留路由本身按真实调用方决定，不为没有调用方的旧路径加兼容层。

本轮**不新增启动模式**。主按钮推荐“创建并启动”，旁边明确“资料绑定成功后进入执行调度”；成功反馈使用“已创建，等待调度”，不能写成“模型已启动”。这是说明现有 active 创建行为，不是新增启动 API。保留现有 `scenario`、Worker 模板与输入保护；不把已有场景功能移除后留到第二轮重做。

首轮预计主要改动：`Projects.vue`、`NewProject.vue`（提取／替换当前创建视图）、`router/index.ts`，以及必要的 `ProjectResourceBatchUploader.vue`／`useProjectResourceBatch.ts`；复用 `Dialog.vue`，只有现有容器确有无法承接的缺口才做最小共享修订。创建 schema、Server 事务与 Dispatcher 不因布局搬迁而改变。

### 4.2 弹窗交互

- 复用现有 Dialog、表单控件与 design tokens；只用 Lucide 图标、简体中文。不要复制参考站主题、另建页面私有视觉体系或新增 UI 依赖。
- 桌面使用能舒适填写两个多行文本区的宽弹窗；窄屏使用可用视口宽度。标题、内容滚动区、底部操作各有明确归属，内容不能靠 `overflow:hidden` 截掉。
- 打开时焦点进入表单，关闭后回到触发按钮；Tab 不跑到背景。次级资料选择器关闭时只关闭自身，不误关父表单。
- 点击遮罩不静默丢稿；Esc／关闭按钮在有用户修改或临时资料时提示是否放弃。默认模板自动填入不单独算用户改稿。无修改与批次时直接关闭。
- 上传／提交中禁止重复动作和直接卸载；请求完成后再关闭，不把关闭等同于撤销请求。用户确认放弃后复用 batch 取消接口；取消失败要保留可重试上下文，不能显示清理成功。项目创建成功后不能再取消已消费批次。
- 服务端明确拒绝创建时保留字段与现有批次，修正后复用，不从头上传。部分上传失败保留已确认成功的成员；未发出和明确失败的文件可在本次页面会话内重试。
- 请求超时／连接断开且无法确认创建结果时，显示“创建结果未确认”，不自动重发或使用普通“重试创建”按钮。提供查看项目列表、保留当前内容的路径；核实前不取消可能已消费的批次、不按标题猜测项目归属。本轮不承诺解决跨刷新或跨网络失败的请求幂等，服务端幂等机制作为后续独立问题评估。
- 只在本次页面会话中保存未提交内容，不新增含 Origin、Goal、文件或凭据的 `localStorage` 草稿。页面刷新不能被宣称为可以可靠恢复本地 File 对象。
- 收到创建成功响应后，项目与输入已经提交。若路由跳转失败，应显示“项目已创建”及进入该项目的动作，不能落入“创建失败，请重试”。不要虚构“先创建、后绑定资料、再启动”的现有步骤。
- 字段错误放在字段附近，上传部分成功与创建未知结果放在可见区域；不能只用瞬时 toast 或 disabled tooltip 表达。

### 4.3 资料不是装饰

资料区将两种来源放在相邻入口，不混淆其语义：

1. **添加文件**：多选、拖入、查看文件名与大小、移除临时批次成员；保留现有独立 ZIP 导入语义及目录结构，不将 ZIP 当普通文件悄悄换掉导入行为。
2. **从资料库选择**：复用现有资料选择能力，查看已选条目并取消本次关联；取消选择不是删除资料库原件。

需要区分“待上传”“上传中”“已加入临时批次”“失败／结果未确认”，并说明创建成功才绑定到项目。状态从当前操作与批次成员派生，不为每个视觉标签另建持久化业务状态。

- 保留现有选择后上传至临时 batch、创建时消费的时机，不改成创建 active 项目后再上传。拖入复用相同处理入口，不新建第二套上传实现。
- 多文件部分成功时保留已确认成功成员，只补未上传／明确失败项；请求结果不明时先核对当前批次，而不是盲重传。没有可确认的恢复依据就显示未知，不假定服务端失败。
- 有尚未完成且用户仍希望带入的文件时不能提交一个缺资料的项目。确需跳过，用户明确移除该待处理项并看到它未参与创建。不取消正常无附件创建能力。
- 保留成员 kind／path 编辑与删除能力，可收进明细而不是占据首屏。资料库与上传资料来源清楚，不把同名文件直接合并。
- 大小、数量、路径、ZIP 与嵌套归档限制继续由已有服务定义；界面如实显示原因，不根据参考站空的 `accept` 属性宣称任意格式可读。
- 上传与关联完成不等于模型已读。必须保留“登记 → 创建事务绑定 → 执行端可取得原件与索引”的链，不能只在表单展示文件名。
- 用户输入资料不是自动接受的发现证据，更不是系统指令。保留原文和来源；不把文件内的指令提升为授权、工具约束或系统提示。
- 本轮不新增 OCR、其他归档格式解压、远程仓库拉取、源码索引平台、资料全文自动拼接或秘密扫描框架；已有 ZIP 导入不是待新增能力，也不能删掉。

### 4.4 首轮直接验收

优先在真实页面查看入口、填写、资料选择与移除、错误反馈、关闭保护、滚动和焦点；选择一个常用桌面尺寸和确有影响的窄窗口即可，不跑全站矩阵。

对存在副作用的创建流程，优先复用最贴近的定向用例或受控接口替身，按本轮实际修改选择：创建成功、部分上传失败后补传、服务端明确拒绝、创建响应不明、创建成功后导航失败、关闭批次清理与连续点击。不为列满这些场景追加整套检查；已有充分信号不重复测试。不要用真实付费项目试错；真实执行路径留待用户明确授权验收。

运行代码修改完成后按项目既有部署方式构建并启动完整系统；这不自动授权访问目标、创建真实项目或调用模型。记录构建生效与功能验收的不同范围。

## 5. 剩余目标之一：场景用途与输入引导（与计划任务连续实施）

### 5.1 不再建设一套“新场景系统”

Arena 已有 `scenario`、服务端 catalog 和可编辑模板；场景还承担执行环境及 Prompt 引用职责，不能被当成纯前端文案删除。第二轮改善使用者对场景的理解，并在同一目录内补足确有用途的输入配置。

推荐的首批产品用途如下，**后两项是拟新增配置，不是已确认存在的默认场景**：

| 场景用途 | 建议处理 | 边界 |
| --- | --- | --- |
| 目标驱动探索／自定义目标 | 保留现有 `goal-driven-v1` 与默认运行配置，作为自由表达入口 | 不为改名另建同义场景 |
| Web/API 安全测试 | 先检查现有 catalog；没有等价项时，在现有配置体系中增加用途清晰的场景与简短模板 | 复用目标驱动运行能力，不新建固定 Web 流程；不要求 URL 格式 |
| CTF 解题 | 同样复用 catalog，提供题目信息、附件说明与期望产物的输入引导 | 不保证解题成功，不把特定题型／靶场答案写入通用内核 |

新用途共享适用的现有 profile／Prompt group，差异先落在清晰的名称与短输入模板，不复制一整套 Prompt／执行画像。实施时核对引用可用性；已有实例若需要补充配置，使用既有配置管理路径定向新增，不清空或覆盖用户条目，不只修改首次建库默认值就宣称现有部署已出现选项。

代码审计为后续候选：虽然当前已有 ZIP 目录导入及只读资料挂载，仍未验证实际多文件代码审计效果，不能以“可上传 ZIP”冒充审计能力。攻防演练、合规检测和专属套餐不纳入本轮。

### 5.2 场景交互与消费

- 前端始终读取现有 catalog；复用 `origin_template`、`goal_template` 展示“此场景建议如何填写”，可展开预览。不新增前端硬编码场景表、`scene_id` 或另一套模板 API。
- 可将通用的“应用执行画像、Prompt 与资源策略”文案改为可理解的用途说明；具体场景内容来自同一目录／模板，不在前端另维护 key 到说明的平行映射。
- 复用 `newProjectScenarioTemplates.ts`。未编辑的空白／自动建议可随切换替换；用户已经编辑的 Origin 和 Goal 都必须保留。希望重用建议时提供明确的“使用此建议”动作，不因后台 catalog 刷新覆盖用户输入。
- 返回默认场景同样保护用户编辑，不清空文件、资料、Worker、项目组或时间设置。既有的未编辑自动模板移除语义不在第一轮顺手改变；第二轮若调整，连同当前直接用例一起更新。
- 最终用户正文仍写入 Origin／Goal；`scenario` 继续按现有 schema 提交，服务端校验并保存运行配置，Dispatcher 按原链消费。不能只更改选中卡片，不提交场景或丢失其运行配置。
- 不另拼隐藏的“场景最终目标”覆盖用户 Goal，不新增专属 Agent、固定阶段、模板市场或后台管理平台，不用历史 coverage 规则定义探索顺序。
- 内置输入模板只写填写引导与简短目标，不含真实地址、账号、凭据、现成漏洞事实或会被自动当成目标的演示 URL。背景与授权的已知差异按第 2.2 节单独处理，不能声称模板保护等同于授权修复。
- 场景快照目前包含运行配置引用，不等于所有 Prompt 内容按项目冻结；本轮不扩展为版本管理平台，也不改变历史项目引用。

直接验收：已有场景不丢失、新配置确实在目录出现、模板预览、用户改写保护、资料保留，以及提交的 `scenario`／Origin／Goal 正确。默认场景仍可自由表达；配置可用和模板进入上下文不等于研究效果通过，不为演示自动启动付费任务。

## 6. 统一计划基础与单次定时启动

本节及第 7 节保留前次计划任务设计，当时属于待实施能力，现已有第 10 节实现记录；不是本次重新建设任务。单次和周期共享持久化计划、时间计算、触发事务及管理界面；本次只按第 11 节改善呈现及时间归属，不从头重做。

### 6.1 已确认的接入点与最小数据关系

2026-10-13 定向源码核对：

- `server/services/project_records.py:create_project_record` 已可接收外部连接；内部创建目前固定 `active`。`project_lifecycle_actions`／`project_lifecycle_action` 和旧状态更新入口会恢复 `paused`，故不能仅用暂停状态承载预约。
- `server/db.py:get_conn` 负责提交／回滚，项目同时支持 SQLite、PostgreSQL；普通事务不默认是 `BEGIN IMMEDIATE`。不能只依靠进程内锁或假设所有查询都已锁行。
- `dispatcher/scheduler/loop.py:DispatcherLoop.run` 是计划消费接入点；`dispatch_cycle.py:_dispatch_available` 在满容量或没有 active 项目时会提前返回，计划消费不能放在该返回之后。
- `server/services/project_resources.py:consume_project_resource_batch` 将原件复制到项目目录、校验大小／摘要并把 batch 标记 consumed；暂存会删除且有 TTL，不能被每轮重复消费。
- `server/services/libraries.py:resolve_current_library_revisions` 和 `bind_library_revision` 支持现有不可变资料版本；`archive_library` 目前只检查项目绑定，新增计划引用必须纳入保护。

上述路径均位于 `cairn/src/cairn/`。推荐以下最小关系，实际字段命名按代码风格落地：

| 持久信息 | 唯一职责 |
| --- | --- |
| `project_schedules` | 归属 tenant／创建者、单次或周期、管理状态、时区／规则、下一触发时间、配置版本。单次关联已经创建的项目；周期保存未来项目的输入与显式授权范围，不为单次复制完整项目表单 |
| `project_schedule_occurrences` | 计划、稳定逻辑时刻键、应触发／实际处理时间、关联项目或跳过／受阻原因；`(schedule_id, occurrence_key)` 唯一，生成项目关联唯一 |
| 计划资料所有权／版本关联 | 第 7.3 节的长期输入，不是另一套上传、解析或资料管理平台 |
| 创建请求去重记录 | 第 6.4 节的请求身份与已提交结果；与“某个计划的一次触发”是不同身份，不能互相替代 |

建议 API 形状：立即创建继续 `POST /projects`；定时／周期使用 `POST /project-schedules`，其中项目输入复用现有创建 schema 的字段校验，按 mode 承载单次时刻或周期规则。返回 schedule 与单次 project ID（周期保存不虚构项目 ID）。提供 schedule 列表／详情、未来时间预览、带配置版本的编辑及管理动作、分页触发历史；这些是拟新增接口，不是现行协议。普通请求保留 tenant 访问检查、用户身份与写请求保护，操作不能越权引用 batch、Worker、项目或计划。2026-10-19 起按重设方案第 15.14 节移除项目组访问检查及必选组要求；取消分类不取消真实资源归属。机器身份消费入口只由 Dispatcher 调用，业务事务仍在 Server。

单次项目增加 `pending`（界面“待启动”），创建事务直接写该状态；已有普通项目保持原行为。同步 Python 状态类型、前端类型／筛选／状态展示和生命周期动作；数据库新增关系走现有双后端迁移，不改已发布迁移、不清库。现有 DB status 列是 TEXT，但 API Literal 和展示映射仍须贯通，不能只改 INSERT。

> 2026-10-15 后续只读核对：上述贯通遗漏了 runtime 消费者。当前 `server/schemas/project_runtime.py:68–72` 不接受 `pending`，但 `services/project_runtime_diagnostics.py:1097–1104` 原样传入项目状态；混合批次可因一个合法预约项目而整体失败，影响任务列表其他行。当前源码缺陷已确认，用户现场是否命中仍未知，未运行测试或接口。修复与定向验收统一纳入 [复测与界面重设方案当前第 14 节](vulnerability-evidence-retest-redesign.md)：复用已有 ProjectStatus，明确 pending 投影，核对单项及混合批次；不前端排除 pending 来绕过，不重新实施整套计划任务。

### 6.2 单次保存、消费与管理

1. 新建弹窗仍先准备 batch 和选择资料。单次保存由同一事务创建 pending 项目、绑定资料／冻结资料库版本、写授权及计划；失败一起回滚。不得先提交 active 再补计划或暂停。
2. 浏览器关闭不影响计划。Dispatcher 在外层循环认证后、获取项目列表及判断容量前，经已有机器身份鉴权的 Server 接口有界处理到期计划；不让前端直调机器消费接口，不把数据库访问或业务事务复制进 Dispatcher。
3. 每个计划独立短事务：按“计划→项目”的固定顺序锁定并重读，确认状态／时间／期限／授权／配置，原子执行 pending→active、写触发关联和推进计划。周期也使用同一消费服务，见第 7 节。遵循两种 DB 的真实写锁语义；取消、改期、编辑、立即启动使用同一锁序和配置版本校验。
4. 单次 occurrence 使用固定键，不随改期更换。已提交的激活不得再次发生；网络重试、并发消费者和进程重启返回同一结果。受阻不是已激活：用户修正后在同一记录上原子完成首次激活，既有事件保留前次受阻原因，不生成新键绕过防重。周期跳过／错过的逻辑时刻已处理，不补跑。不提前提交“已领取”再异步激活，因此不需要租约、回收队列或额外任务引擎。
5. 激活只代表“等待调度”。Worker 暂无空位继续走现有容量管理；Worker 已删除／不可用、场景配置失效或资料缺失才进入需要处理，不伪装为容量等待。可预见的业务受阻保存原因；未预期异常按真实错误记录，不吞掉并冒充成功，单个坏计划不拖死整个扫描。
6. 单次停机期间到期，恢复后仍有合法执行窗口则启动并显示延迟；否则保留 pending 与受阻原因。没有运行 Dispatcher 时显示等待后台处理，不用 Server 健康检查冒称计划正在执行。

管理入口放在项目列表的“计划任务”视图／页签，复用现有列表与详情模式，不新建运营控制台。单次项目列表和详情显示时间、时区、计划状态及原因，提供改期、取消预约、立即启动。普通 resume、旧 PUT/status 和其他派发入口不能把 pending 提前改为 active；“立即启动”必须通过上述原子事务。

取消只撤销自动启动，保留待启动项目、输入与原计划关联；用户之后可明确立即启动或重新设置时间，仍使用同一单次键。已经触发不能重新排期；取消输给触发时返回“已触发”，停止运行使用原有停止动作。项目删除与计划触发也必须采用相同锁顺序，明确取消尚未触发计划，不能留下继续访问已删项目的活动预约。

### 6.3 时间语义与共享计算

- **启动时间**决定何时进入调度；**`explore_deadline`** 仍是执行停止绝对时间；**`authorization_expires_at`** 仍是授权绝对到期时间。三者独立，`null` 保留现有含义，不自动设置 24 小时、30 天或按周期续期。
- 单次保存含时区的绝对时刻和显示时区。周期保存 IANA 时区、每日／每周规则与本地时间，由后端统一计算 UTC 时刻。默认使用浏览器检测时区并允许修改；不使用服务器本地时区猜测用户意图。
- 使用现有依赖和 Python 标准库 `zoneinfo`；确认部署可访问时区数据。不自动新增 Cron／调度依赖，缺失运行前提时如实报告，不退化成错误的 UTC 计算。
- 预览未来 3 次与实际消费者调用同一后端时间函数，前端只展示结果。单次不存在的本地时间明确拒绝；重复时刻要求用户选择明确偏移。周期夏令时缺失时刻跳过，重复时刻固定选较早的一次，并在预览注明。
- 起始边界包含该时刻；结束边界不包含。周期可选结束日期（在所选时区解释为该日结束边界）或成功生成项目次数上限，允许均不设置。停止／授权时间若已填，所有未来实例仍受同一绝对边界限制；界面标出由此更早结束，不把原绝对截止时间暗改为“每轮运行时长”。
- 周期正常扫描允许到期后 60 秒内处理一次，避免将循环延迟误判为错过；超过该容差的历史时刻不补跑，记录错过范围并推进到未来。长时间停机不逐条生成巨量历史记录。容差是调度拾取窗口，不是授权延长期，也不是研究超时。单次遵循第 6.2 节的延迟启动规则，不套用此跳过策略。

### 6.4 请求幂等与 A 的未知状态恢复

A 已有一个确定使用阻塞：`NewProject.vue:onBeforeRouteLeave` 在 `creationUnknown` 时总是拦截，点击“查看项目列表，保留内容”只是隐藏弹窗，之后仍不能进入项目详情核实。本次直接修正，不再加一层路由禁止条件。

- 为现有项目创建和新增计划保存提供窄范围服务端幂等键。前端一次明确提交生成一个随机请求 ID，未知结果重查／重发使用原键和原 payload；不是每次点击生成新键。服务端以 tenant、用户、操作类型与请求 ID 唯一约束，记录规范请求摘要和已提交 project／schedule ID，与业务写入同事务完成。
- 同键同内容返回原结果，即使 batch 已消费也先命中原结果；同键不同内容明确冲突。摘要基于提交内容，不掺入会随时间变化的场景／资料库解析结果；仅首次执行解析当前配置。明确校验拒绝且未提交后，用户修改输入可开始新一次请求；未知时不默默换键再建。
- 提供按请求 ID 查询已提交结果的受鉴权入口，授权范围与创建一致；一次“尚未查到”不能证明在途请求已失败。仅恢复该请求，不按项目标题猜测归属，不建立通用重试平台。
- 去掉未知创建对无关页面导航的永久阻断，允许查看列表／详情。页面会话可用 `sessionStorage` 仅保存不透明请求 ID 与操作类别以支持返回查询，不存 Origin、Goal、文件、凭据或完整 payload；不承诺跨刷新恢复 File／未提交正文。首次实施前遗留的无幂等键未知请求，仍不得盲重发，可正常浏览并明确无法自动关联。
- 已知成功后导航失败只重试进入已知项目。保存周期计划后导航到计划详情，不能假称已创建首轮项目。临时 batch 的创建／ZIP 上传未知机制不在本次扩成完整去重平台，保留真实限制。

## 7. 前次交付设计：周期运行

### 7.1 创建、重复与重叠

- 新建弹窗提供每日／每周（可选星期）、本地时刻、时区、起始边界、可选结束日期／成功生成次数及未来 3 次预览；默认不上来要求 Cron。保存后仅生成计划及长期输入，首轮在第一个未来有效时刻创建，不暗中立即启动一轮。
- 每次有效触发调用同一个项目创建服务，生成独立项目、原始事实、资料绑定及授权，默认进入 active 等待既有调度。计划锁、唯一 occurrence、项目创建和推进下一时刻在同一事务提交；不清空旧项目，不复制旧 Finding 或执行历史。
- 稳定逻辑时刻键采用规则计算出的 UTC 时刻；改单纯展示、暂停恢复和重试不能改变同一次触发身份。计划编辑采用配置版本，已经处理过的逻辑时刻不再生成项目；不以编辑版本绕过 occurrence 唯一约束。
- 默认上轮未结束就跳过并记录原因，不排队堆积、不自动终止上轮。active（含等待容量）、paused，以及虽进入终态但仍有未结束／清理未确认执行的项目均视为未结束；复用当前任务／物理执行状态判断，不只检查项目标签。此判断用于计划实例不重叠，不改平台其他项目并发策略。
- 成功生成次数只计已原子关联的项目；跳过、错过、受阻均不扣次数。达到次数／结束边界则计划完成。已过授权／执行停止边界或关键配置失效转需要处理，不自动反复创建失败项目。

### 7.2 管理体验

“计划任务”视图列出模式、规则摘要、时区、下一次时间、状态、上次结果与最近项目；详情显示运行历史和每个项目入口。周期提供暂停、恢复、编辑未来配置、停用：

- 暂停只阻止未来生成，不停止正在执行的项目；恢复从下一个未来时刻继续，不补发暂停期间的轮次。
- 编辑时间、范围、Worker、场景及资料等未来输入，复用创建表单／配置校验，不复制第二套创建逻辑。活动计划编辑与消费由相同锁和版本判定串行；界面说明只影响尚未生成的项目。
- 停用是本次的删除／移除操作，停止未来触发，保留计划记录、输入及历史项目，不做硬删除或资料级联销毁。已经生成的项目需要停止时走已有项目动作。
- 受阻原因要可理解，提供相应编辑／恢复入口；列表显示短状态，诊断按需展开。不得显示“已运行”却只有一条计划记录。

### 7.3 资料跨周期消费

采用**计划持有持久输入，每轮复制／绑定为独立项目资料**的直接方案，不使用隐藏模板项目，也不把用户私有附件自动发布到公共资料库。

1. 周期保存消费本次临时 batch 一次，将原始成员及 kind／path／大小／摘要持久化为计划所有的输入。复用现有资源存储根、路径／ZIP 限制和字节校验，按 schedule 隔离目录。可增加专用的计划资源归属记录，但上传解析与字节复制逻辑提取复用，不复制整套服务或新增通用对象存储框架。
2. batch 的消费归属扩展为项目或计划，DB 保证至多一个所有者；状态／查询／取消／清理路径一起适配。成功提交后可删临时暂存，TTL 清理只能清理 batch 暂存，不能删计划持有原件。保留已有项目批次数据，不靠伪造 project_id 填入 schedule_id。
3. 每轮在项目可被 Dispatcher 看见前完成资料复制和大小／摘要校验；得到独立项目资源记录，继续走现有 advisory bundle／只读挂载。资料缺失、权限或摘要错误时不得提交无资料的 active 项目。
4. 资料库在保存／显式编辑计划时解析当前不可变 revision，计划保留版本及摘要关联；每轮绑定该版本，不静默换成 latest。界面展示固定版本，用户选择更新才影响以后轮次。资料库归档／删除的引用检查包含计划绑定，不能只查项目绑定。
5. 修改计划资料不影响已生成项目；项目删除不影响计划长期输入，计划停用也不删除历史项目原件。需要资料调整时用既有上传组件和批次路径，不保留浏览器 File 作为定时器依赖。
6. 文件系统与 DB 不是同一个事务：复制失败或外层事务回滚清理本次新建副本，不能删除原 batch／已提交资料；崩溃残留不能被当作已绑定输入。重试只依据已提交归属和摘要，定向处理本次操作遗留，不增加全局修复器。按已有文件配额控制一次事务的工作量，不引入异步半成品 active 项目。

### 11.5 上传：一个入口，取消普通文件的人为大小上限

**产品决定：选择文件与拖入统一入口；ZIP 自动沿既有展开流程处理；普通单文件不设应用层大小上限。** “不设上限”指不再按预设 MiB 门槛拒绝，不保证无限磁盘、内存或代理容量，也不等于任意格式都能被模型解析。

1. “添加文件”支持混合多选及拖入，二者使用同一个分类入口：`.zip`（扩展名不区分大小写）走既有 ZIP 接口，其他走普通原件上传；浏览器 MIME 只作辅助，ZIP 内容有效性仍由服务端检查。说明“ZIP 将展开并保留目录”；损坏 ZIP 明确失败，不静默回退成普通文件。没有扩展名的文件仍按原件，不为猜测格式读取完整大文件。移除独立 ZIP 按钮和独立选择交互，不必合并后端 `/files` 与 `/zip`。
2. 沿用既有上传队列、临时 batch、逐项成功／失败／未知、路径／kind 编辑和创建消费。混合上传单项失败不抹掉其他成功项，只重试明确失败项；结果不明先按现有能力核对，不引入盲重放。ZIP 内嵌归档不递归解包，现有未知 ZIP 的恢复限制不因入口合并而假称解决。
3. **贯通普通文件的所有门槛**：前端 `projectResources.ts`／`useProjectResourceBatch.ts`，配置响应 Schema 与类型，服务端流接收、批次加入、用户暂存字节限额、最终资源集合、创建／已有项目导入、计划持久输入及校验消费者。10 MiB 单文件、100 MiB 总量、200 MiB 暂存是源码默认值，不是部署实值；若总量和暂存仍能拦下一份普通大文件，就不能标“不限大小”。本需求下移除普通上传适用的人为字节门槛，不把它改名为总量限制继续生效。
4. ZIP 的原包、成员、展开量／数量、压缩比、路径和特殊文件规则保留。当前 `max_file_bytes` 同时承担普通文件和 ZIP 成员限制，需要明确拆开语义或删掉已不需要的普通限额字段；不得用零／极大正整数伪装不限（当前 `_positive_env` 只接受正整数）。集合校验保持来源一致，不靠临时 UI 标记绕过规则，也不建立两套限制事实。文件数量、开放批次数等非字节限制未被本需求取消，仍如实显示原因。
5. 资料库文本上传／保存另有 2,000,000 UTF-8 字节上限（`schemas/knowledge.py:24-32`、`services/libraries.py:76-85,436-448`）。本次“单文件暂不限制大小”同样适用于受支持的资料库文本文件，后续上传轮应处理该链，而不能项目可传、资料库仍暗中拒绝。保留严格 UTF-8、有效路径、不可变版本与引用语义；不因此新增 ZIP 库导入、OCR、PDF 解析、远程仓库拉取或二进制编辑器。
6. 后端项目文件接收已为流式，应继续利用，避免 `read()`／base64 整份复制来取代真实上限。当前未知上传核对使用 `file.arrayBuffer()` 计算摘要，大文件下不能悄悄耗尽内存；定向调整该恢复路径，无法可靠核对时保留“结果未确认”，不取消摘要校验来假报成功。资料库文本编辑链本来会持有全文，解除产品门槛不承诺无限文本编辑性能；遇到真实资源错误保留草稿／原件及明确错误，不伪造保存成功。
7. 不预设要建设分片上传、断点续传、异步导入平台或新增依赖。只沿现有传输、存储和资料包消费者核对真实阻塞；实现轮检查实际代理／传输上限，发现基础设施仍有限制则修正本轮相关配置或明确尚未完成，不仅改提示。取消应用门槛不能以让 Worker 最后取不到文件为代价。
8. 共享上传器也被 `ProjectWorkspace.vue:446-474` 及计划编辑使用，统一入口／大小行为必须同源；这些消费者要验收，不顺带重做它们的整页布局。同步现行协议、限制说明和直接相关用例，不修改历史业务材料。

定位重点：`cairn/src/cairn/server/services/project_resources.py:349-371,540-587,654-755,1013-1091`；`services/schedule_resources.py:91-99`；`schemas/resources.py:11-21`；`cairn/frontend/src/api/types/projects.ts:418-429`；前述上传组件／composable／资料库文本链。精确改动在该轮接手时按最新代码收敛。

### 11.6 时间：统一操作入口，不混淆不同事实

**推荐：删除独立“执行边界”表单块；新建立即模式不设人工时间截止；定时的开始与可选停止在同一处配置。** 复用现有项目 `explore_deadline` 作为停止截止的权威字段，不再增加与它需保持相等的 `stop_at`。这是界面／字段归属整合，不重建调度器。

| 场景 | 新建／编辑时的目标行为 | 不允许的解释 |
| --- | --- | --- |
| 新建立即启动 | 默认无启动预约、无执行截止、无另一个授权到期表单；创建请求按契约显式发送未设期限。正常目标驱动结束，不因预设时间截断 | 不是强制永远 active；手动停止、真实故障、实际授权／资源约束与合理受阻仍成立，不能伪称目标已完成 |
| 单次定时 | 开始时间必填；停止时间默认选择“不限制停止时间”，用户选“指定停止时间”后再显示日期／时间输入，必填且须晚于开始。两者位于单次时间设置内，收起后一起显示时间和时区 | 不把未限制时间说成永不停止，不把启动时间写入截止，不将到点激活写成 Worker 已运行，不因尚有剩余时间阻止自然提前完成 |
| 每日／每周 | 复用已存在的重复规则及预览；若设置“执行停止时间”，仍是所有后续实例沿用的同一个绝对截止，不悄悄改成每轮时长 | 不新增每轮停止时长、不自动停止上一轮、不把周期规则的结束日期冒充活动项目停止时间 |
| 周期结束日期／次数 | 在重复设置的次要项明确为“停止生成新项目”，保留现有语义；与执行停止截止分开说明 | 结束日期、暂停、停用只影响未来生成，不得显示成运行中项目已停止 |
| 历史项目／计划 | 原期限、grant 和已生成项目配置照旧；明确显示既有更早约束。修改未来配置不追改已经创建的项目 | 不因删表单批量置空历史期限，不用一次计划编辑自动续期授权或延长活动项目 |

- 当前立即创建的两个时间默认已为空；`services/assessment_policy.py:129-143` 明确不从场景／创建时间派生项目截止，`services/project_records.py:215-269` 只校验并持久化传入值。不存在需要新建一套“不限时引擎”的证据。实施只核对这些直接消费者，防止隐藏旧值继续提交或新改动引入默认时限；不为“直到完成”去掉单工具超时、heartbeat、租约、有界故障处理或资源约束。
- 新建入口不再要求重复设置授权到期。新创建且未声明期限时沿用已有显式 `authorization_expires_at=null`；这不取消 target 授权，也不放开空范围受阻。对已存在有限授权的项目／计划，原始值和重新授权入口保留在对应管理动作／详情，不静默取消或续期。执行截止和 grant 是不同事实，不将同一日期机械复制成两份权威状态。
- 从定时切回立即：摘要只显示当前有效方式，不继续显示或发送旧预约／停止时间，也不为解释隐藏草稿新增常驻段落；可在本次表单会话保留定时草稿，切回时恢复，但有效提交从当前模式唯一派生。编辑已有计划不借模式切换转成新立即项目；单次计划的“立即启动”继续走原原子激活，已有停止／授权约束须可见，取消它们是明确编辑，不是自动抹除。
- 定时时间沿用当前共享 IANA 时区／绝对时刻计算，不把停止字段继续当浏览器本地值而忽略选择的计划时区。开始与停止的错误分别就近提示，收起后显示时区；停止早于开始直接拒绝。改期同时检查既有截止，不能只改开始导致保存后无法执行。单次更新现有契约为顶层 `explore_deadline` 省略保持、`null` 清除、有值更新；重复计划使用项目输入内的字段，不能在重排表单时混用（`schemas/project_schedules.py:100-123`、`services/project_schedules.py:228-271`）。
- 停机后恢复／容量等待跨过停止时间不得再开始研究；需要区分“错过执行窗口”和“目标完成”。重复计划后续触发继续受同一截止约束，不产生立即过期项目。目标提前完成按原真实交付结束，不为了等到指定停止时间继续调用模型。
- **“停止时间”是停止继续研究的截止，不是该秒物理清理已经完成的承诺。** 已确认代码有 deadline 收敛、心跳拒绝触发取消、单 Run 截止裁剪及 runner／容器超时；应复用并补齐必要缺口，而不是只靠 UI 定时器或停止生成计划。到期应停止新研究派发并请求取消在途研究，保留已有资料与成果；清理／交付是否完成按实际状态展示，失败或未知如实保留，不能用 stopped 标签当全部进程已退出证明。现有报告执行使用自身 timeout，不与研究截止同样裁剪；截止后必要报告／清理不等于继续研究，不为追求“到秒全停”丢掉交付。
- 定向源码注意项：`server/services/project_reason.py:111-118` 和 `server/routers/intents.py:218-227` 的 heartbeat 会推进收敛；`dispatcher/runtime/heartbeat.py:99-128` 收到 409 触发取消；`dispatcher/tasks/delivery.py:203-218` 将运行截止裁为任务超时／执行截止／授权截止的较早值。`server/services/assessment_convergence.py:472-490` 的待清理查询带 `pause_requested=1`，而 deadline 分支自身未设置该标志；这是需要在时间轮核对的静态证据，**未动态复现，不能直接宣布到期必然已物理停止或必然泄漏进程**。

1. 实际受控页面确认六处指定静态说明消失，探索场景默认展开、手动收起可保持、选择仍保护用户改写；必要异常摘要及操作仍可达。

因此，“固定三个 Worker”应理解为用户这套默认配置，不是产品永久只能有三个 Worker。若确实需要一人一职，将三条 Worker 的 task_types 分别设为仅 bootstrap／reason／explore；仅改显示名不足以绑定角色。保留现有多角色能力：一个支持三角色的 Worker 也可构成有效组合，不强制恰好三个、不为每个角色增加独立执行组织。旧调度方案中“缺 Bootstrap 回退 Reason”等描述不符合本轮代码，不能作为实现前提；本轮不借机全篇重写旧调度文档。

#### 本轮最小完整改动

1. **唯一默认来源是现有模板。** 为 `worker_templates` 及相应 API 类型增加 `is_default`，默认 false，同 Tenant 至多一个 true；使用事务与 Tenant 范围唯一约束完成切换，不另存一套 default IDs、角色映射或浏览器偏好。模板中仍只引用 Worker ID，模型、task_types、并发仍归原 Worker 配置所有。已有模板不按名称、创建顺序或数量猜默认；迁移不自动修改已有模型／Worker。
2. **首次配置有真实入口。** 在新建弹窗现有执行设置里提供“保存为默认组合”：首次手动选好一次即可保存；选现有模板可设为默认，手工组合可通过既有 CRUD 创建或更新默认模板。明确动作才持久化，不在普通勾选／提交项目时暗存偏好；保存默认本身不创建项目、不调用模型。不要只修改没有挂载的 `WorkerTemplatesPanel`。不为这一个设置新建管理页；沿用已有控件、短反馈和错误展示。
3. **以后新建免选择。** Worker 与模板查询完成后，初次初始化完整默认 IDs；正常执行设置仍折叠，短摘要能看到使用的组合，用户无需再打开勾选。保留高级的“本次自定义”和主动恢复默认。初始化后普通查询刷新只更新可用性，不改选组；用户编辑过、提交中、创建结果未知时均不能覆盖草稿。三个新建入口共用同一有效 IDs：立即、单次、重复（每日／每周）；切换启动模式不重复应用模板。
4. **失效不静默换人。** 默认尚未设置、模板被删除、成员缺失／禁用／模型配置不可用、缺少必需角色时，具体原因可见，设置区按需展开，允许明确修正或本次自定义。不沿用过滤失效成员后继续提交的语义，也不选首项、全选、换模型或回退其他池。已经解析到草稿中的失效 ID 保留供解释与显式替换。模板查询失败不能当“没有默认”，不能在异步状态未稳定时宣称默认已可用。
5. **覆盖校验针对确实无法启动的输入，不增加形式门槛。** 保存／设定默认模板时，以及新建目标驱动项目和计划输入时，服务端在现有归属／可用性校验之后，以所选 Worker 的 `task_types` 并集确认 bootstrap／reason／explore 齐全，给出具体缺项。提取一处共享校验供相关消费者复用；前端可派生同样的就近提示，但最终以服务端为准。不要直接让共享选择 helper 的所有调用都强制三角色：普通非默认模板可以只保存部分能力，历史项目显式重绑也不因本轮被迫增加不再需要的 Bootstrap。容量暂满、Dispatcher 暂离线不等于 Worker 配置缺失，不做在线模型探测、不阻止合理排队，不恢复固定 Explore 次数。
6. **继续显式绑定，不扩大默认的职责。** 新建请求仍提交完整 `tenant_worker_ids`，复用项目／计划的持久绑定、幂等与创建恢复链；不新增“省略 Worker 则服务端猜默认”的另一套创建语义。API 直接调用者仍显式指定 IDs。默认变化只影响以后新打开的创建草稿，不追改已存周期输入、旧计划、旧项目或未知创建请求；周期触发不重新读取最新默认。编辑旧计划优先恢复其显式配置，不在编辑其他字段时自动套默认。
7. **旧测试项目可按需删除，但不是实施前提。** 用户已明确它们是无关测试项目，确有需要可在实施会话核对实际实例、项目列表与执行状态后，列明范围并走正常项目删除流程，不为保留它们新增兼容分支或历史修复器。默认组合本身不需要删项目；没有必要就不删。不扩大为清库、删除未确认的计划、模型、Worker、凭据、共享资料库或其他资源；关联材料按现有项目删除语义处理。正常流程不能安全处理在途执行时说明具体阻塞，不用 SQL 强删绕过。分析会话不据此操作项目。

涉及的必要位置：`NewProject.vue`、前端 `api/types/worker_templates.ts`／既有模板 API、后端 `schemas/worker_templates.py`／`services/worker_templates.py`、DB schema／迁移，以及新项目／计划输入的角色并集校验直接调用方。新建共用组件已承载重复计划编辑，必须保护这条消费者；不借此重做工作区、模板管理平台或 Dispatcher。实际改动协议同步 `docs/specs/server-protocol.md`。

#### 并发建议与生效边界

以**主要跑单个项目、尚无容量测量**为前提，推荐以下起步值，不是不可修改的架构上限，也不是已经改好的运行配置：

| 设置 | 建议 | 含义与理由 |
| --- | --- | --- |
| 专职 Bootstrap Worker `max_running` | 1 | 初始化通常只需一路；跨项目也共享此槽，多个项目集中启动时会排队 |
| 专职 Reason Worker `max_running` | 1 | 先维持一路决策；单项目已有互斥，设 1 主要限制跨项目共享容量，不是新加单项目防重复机制 |
| 专职 Explore Worker `max_running` | 3 | 一条配置可并行承载三次 Explore，不用新建三个 Explore Worker；先给互补方向一定并行度，避免一开始把模型／浏览器／目标负载拉得太高 |
| `runtime.max_project_workers` | 4 | 单项目所有在途任务合计上限；为 3 Explore 与 1 Reason 的重叠留下容量空间，不是强制四路，也不是调度器提供了独立 Reason 预留 |
| `runtime.max_workers` | 仅这套组合跨项目满载时，5 个槽可覆盖 1+1+3 | 全局上限若已有更高值无需为本轮修改；其他组合／多项目需求另算，不能一律降到 5 |
| `runtime.max_running_projects` | 本轮不改 | 这是 active 项目的接手数，不是任务槽，不应把它当 Explore 并发输入 |

真实可新增任务数同时受 Worker 剩余槽、项目剩余槽与全局剩余槽限制（`dispatcher/scheduler/worker_runtime.py:279-284,540-544`；`dispatch_cycle.py:61-64,270-288,340-349,486-487`，均在 `cairn/src/cairn` 下）。`deploy/dispatch.yaml.example:4-8` 的示例为全局 8／项目数 3／单项目 4，**示例不是正在运行的值**，因此本轮没有理由盲目调高全局配置。

- 三个角色不是三个必须常驻的模型进程。Bootstrap 通常先发生，Reason 与 Explore 是否重叠还取决于可派工作和触发条件；配置容量不证明实际一直有 3 路 Explore。报告等现有交付路径继续沿用原 Worker 能力，不额外引入第四角色或独立并发池。
- `max_running` 是同 Worker ID 在当前 Dispatcher 内跨项目的共享容量，不是每个项目各享 3 路。单项目总上限设为 3，则 Reason 与 Explore 合计最多 3，而不是 1+3。
- 三个 Worker 即使使用同一 Model／Key，仍按 Worker ID 分别计数，不会自动共享供应商配额；1／1／3 不是获得五份独立模型限额，也不是 HTTP 请求速率限制。多 Dispatcher 的全局统一限流不在本轮，不能拿本地计数证明它。
- 本轮不自动改现有 Worker 的并发／角色、模型、运行 YAML 或 revision，不偷偷重绑仍保留的项目。并发使用现有 Workers 配置入口一次设置即可；修改已有 Worker 会使旧绑定失效的事实必须说明，但不因此扩成热更新重构。旧测试项目若确需清理按上节授权处理，不将重绑／删旧项目作为新建默认功能的强制操作。
- 先以 3 路 Explore 使用；出现供应商限流、超时、内存压力或共享登录态冲突可降到 2，确认有独立工作和资源余量后再考虑 4。没有硬件、服务商限额和实际研究收益证据，不推荐直接 8／16，也不宣称 3 是最优。

#### 二、创建提交：局部错误与服务端事实分开

1. **请求 ID 支持现有部署方式。** 将创建两条分支收敛为单一 `crypto.getRandomValues` UUID 生成实现，保持 UUID 格式、随机强度和服务端去重身份。不要简单删 request_id、用 Math.random／时间戳、每次恢复换键，也不新建能力探测平台或引入 UUID 依赖。若随机源本身失败，明确显示请求尚未发出的本地错误，表单可修正／关闭；不将其记为创建未知。
2. **可选缓存不拥有创建成功与否。** `sessionStorage` 只保存不透明 ID／operation，原 payload 已在内存；局部处理该缓存的不可读／不可写／损坏值，返回可供界面显示的明确结果。失败时不阻断本次提交，不删除内存恢复依据，短提示跨刷新查询入口未保存；不假称能跨刷新恢复正文或 File。读取端（含 `CreationRequestRecovery.vue`）与 forget 同源处理，不复制多个宽泛 catch。存储是可选能力，本条不是为未知历史结构建设兼容框架。
3. **错误边界以副作用为准。** 真正 API 请求异常才按已知拒绝／结果未知判断；本地准备失败不应伪装为已发出，服务器已确认成功后缓存清理、toast 或导航失败都不能撤销该成功事实。所有提交路径通过 finally 释放 busy；未知时保留原键原 payload，不自动重放或允许换键盲建。具体已获得的诊断在现有错误／展开区域可见，不只剩通用未知句子。
4. **默认初始化只保护资源选择。** 全表单 `userEdited` 继续服务脏表单关闭保护；默认 Worker 首次应用应判断 Worker／模板是否被手动修改，不能因为先写了名称／Origin／Goal／项目组就跳过。保护当前手选、旧计划显式绑定、提交及未知请求；初始化后刷新只更新可用性，不覆盖选择。不将临时容量不足当配置无效，不按名称／顺序猜默认，缺配置和必填错误保持可见。

#### 三、Origin 作为新建唯一用户范围输入

1. **界面不再重复填写。** 删除独立“明确授权的目标”、添加／移除控件、对应长文、专属状态／校验／样式及以 targets 数量为核心的空范围摘要；不把它改装成隐藏高级输入、候选勾选、预览确认或长篇 tooltip。Origin 原输入承接对象、已知资料、授权和排除；Goal 保留。新立即／单次／每日／每周不人工发送 `targets: []` 来制造旧空集合语义。预览及重复编辑与实际提交一致，保留现有资料、时间、Worker、请求身份和未知恢复。
2. **只在现有授权合同补齐真正缺失的信息。** 新 Origin 来源 grant 的 scope descriptor 绑定已存 Origin Fact 的来源身份及原文摘要，由现有 scope projection 校验；正文原件仍只在既有 Fact／计划输入所有者内持有，不复制成隐藏“最终授权说明”，不裁剪或重写原件。保留现有期限、epoch、执行代际及身份校验；范围来源和版本从持久 descriptor 取得，不能仅按当前 Target 数量猜测。新来源必要的 descriptor 格式是本轮语义变化，不新建审批／授权平台。
3. **停止正则命中即授权。** 新 Origin-only 创建不再调用全文地址提取来写 seed/approved；最小实现可以完全不自动写 Target，利用既有 Bootstrap 理解和 Fact 产出即可。不新增模型预检、Bootstrap Target 输出 Schema 或“先抽取、再自动批准”流水线。以后有用的地址索引也只能是线索，不能取代原文或许可背景／排除目标；附件、检索内容、重定向、历史发现和模型输出都不能自行扩权。Origin 不含 URL 仍可创建、准备和研究资料，不能转成“必须解析出地址”的隐性必填。
4. **贯通计划的真实输入生命周期。** create/update 解除必须显式 targets 的字段约束，保留请求身份、资料归属、时间及版本校验。单次创建的 pending 项目即固定来源与原件；周期的既有 project_json 冻结来源选择及原始输入，每轮复制同一份已保存授权输入，不在触发时从新增资料／发现／默认配置重新扩范围。新 Origin 来源不再因结构化 targets 为空进入 EMPTY_SCOPE_REASON；真实期限、权限、Worker 或资料问题仍按原机制受阻。
5. **不静默重解释实际存量，不把历史保护等同于永久双入口。** 本轮实现保留显式 targets 路径及其原 grant／范围来源，但“源码存在该 API”不能证明已有独立外部调用方或必须长期保留两套新建方式；此前将显式 API 与已存计划概称为“真实调用方”的判断证据不足，在此更正。实施记录报告当时计划为 0，本分析未重新查询实际数据。现有创建参数的缺省／显式区别、project_json 和 descriptor 版本已经表达来源，不再增加同义开关。实际旧 `targets: []` 不应被读成新的 Origin 授权，旧非空集合不能在编辑无关字段时被删除或从背景补入；保护已有材料与授权语义仍是底线。用户取消重复填写的要求本身也不等于批准删除 API、迁移存量或重新授权；如后续收缩旧入口，应以实际调用和数据影响为依据，不为架构纯粹另起全面迁移。本轮不自动转换历史来源、批量迁移 grant 或清库；每轮未来实例使用自身 grant，同一计划的来源与授权输入不漂移。
6. **实际执行必须消费同一来源。** Bootstrap 已有 Origin；Reason／Explore 直接引用同一个 Origin Fact 原文作为本轮边界上下文，不依赖从庞大图谱偶然读到。将 grant 来源／版本投影至现有执行上下文，按来源选择权威范围；替换新 Origin 路径上仍要求只用 seed/approved 的冲突 Prompt，保留旧显式目标路径的真实限制。优先复用同一范围投影／片段，不复制三份各自推断来源的策略。核对 Prompt group／revision 的真实选用链，修改未消费的种子文件不算生效；不要批量覆盖用户自定义 Prompt 或变更历史授权。
7. **自主研究与边界如实表达。** Origin 明确授予的对象／动作内可自主研究，背景引用和排除内容不构成许可；仅资料任务可以开始，不因缺少 OS 网络隔离证明统一拒绝。若将要进行的外部动作缺乏明确范围，利用现有受阻／补充信息表达提出具体需要，不新增每步审批、不堵住无关资料工作。自由输入不等于自动全网许可，模型遵循范围不是网络硬隔离保证；本轮不建设沙箱、代理白名单或网络网关，也不宣称硬隔离已经实现。

本轮必要上下游是创建组件／请求引用缓存、项目和计划 schema／服务、现有授权合同／摘要投影、执行上下文／实际 Prompt 消费和协议；不是只删前端的一行文案，也不是全仓安全限制清扫。删除独立 targets 与修前端提交属于同一轮用户可用路径，无需要求用户先用付费任务验证其中一半。

#### 四、最少直接验证与交付边界

- **入口问题优先用受控页面判定。** 在普通 HTTP 非 loopback 的浏览器环境，或明确模拟 randomUUID 不可用的等效浏览器条件，使用已有 API 替身验证一次立即及计划提交确实各发出一份预期请求，得到清楚反馈；说明所测上下文，不能只跑默认 localhost 后宣称局域网已验证。无需创建真实活动项目。实际按钮若禁用，直接核对可见原因，不能把校验阻断和抛异常混成一个问题。
- **对两个局部机制选择少量覆盖。** 验证可选缓存写入／清理失败不锁死表单、不把已成功变未知；未知恢复仍为原键原载荷。延迟 Worker／模板响应，先只改正文应自动采用默认，手选 Worker 后不得覆盖；不重复跑已无影响的默认唯一性全套。
- **授权输入用真实隔离服务而非仅 mock 成功。** 利用现有测试设施检验：明确授权正文的新 Origin 项目不生成正则 seed；带参考／排除地址不会将它们直接加入许可集合；纯资料 Origin 无地址可创建，并通过新语义的单次／周期消费；grant 摘要绑定已存原文；同一周期后续实例不从新资料扩范围；旧显式 targets 和旧 grant 语义不漂移。页面替身不代替这些事务与摘要证据。
- **上下文证据与研究效果分开。** 用既有上下文构造路径核对三类实际任务均取得原始 Origin、正确来源和不冲突的执行规则，旧项目仍取得旧范围；不为本轮调用付费模型或把静态 Prompt 断言当作真实遵守边界／发现效果证明。不默认全量测试、lint、浏览器矩阵或新验证平台；按实际改动选择最贴近的少数用例即可。
- 同步 `docs/specs/server-protocol.md` 的创建来源、计划字段／触发和恢复行为。按部署方式正式构建并使实际完整系统加载前后端、Dispatcher 与生效 Prompt；只有容器内资源真的改变才重建 Worker 镜像。活动研究／到期计划使重载可能触发费用时先获授权，不自动恢复、重跑或创建真实项目／计划，不访问目标、不清库或删除项目，不批量改 Worker／并发。
- 在第 10 节分别记录源码已实现、直接验证、实际部署、用户使用与真实研究未验收；如前述用户当次根因仍无证据，就继续明确该未知，不拿修掉候选缺陷冒充已确认当次故障。完成本轮停止，不恢复资料库、上传、时间内核及其他历史待办，不 commit／push。

#### 唯一推荐的下一轮：计划消费故障不扩大为研究循环故障

**证据与具体条件：** `dispatcher/scheduler/loop.py:218-252` 将 `consume_project_schedules` 放在 `list_projects`、`_cancel_inactive_tasks`、`_reap_futures`、结果收口和 `_dispatch_available` 之前；`dispatcher/protocol/client.py:86-98` 对端点 HTTP 失败抛请求异常，对计数形状无效抛 `ValueError`。因此，在其他项目接口仍正常但计划端点独立失败时，前者经 `loop.py:253-271` 跳过整轮，后者经 `:272-289` 退出并 close。已有控制观察与收尾不应依赖新计划能否生成。`server/services/project_schedules.py:461-484` 的单计划错误计数已有局部处理，应保留；本问题是整个消费请求失败，不是所有单计划受阻都会拖垮循环。本次没有运行故障证据，也不将累计 diff 当成最新 Origin 轮次新增。

**最小取舍：** 在现有循环中分开已有项目控制／收尾与附加计划消费的失败边界，正常到期消费仍须在无 active 项目或容量满时执行，新实例仍正常进入调度。只局部处理可识别的计划请求／响应失败，使用已有日志／诊断表达，不返回假成功、不把未知副作用当未发生、不加入同轮盲重试；服务端 occurrence 幂等及事务照旧。认证失败、机器身份变化和核心项目读取失败仍遵循原有安全边界，不能借局部继续派发绕过它们。不要把整个 loop 包进宽泛 catch，也不新增调度器、消息队列、熔断／恢复平台或全局状态。

**直接验证：** 优先在既有 `cairn/tests/test_dispatcher_runtime_observations.py` 的循环替身上定向验证计划端点 5xx／请求失败与无效响应时，已有项目控制、收尾仍可到达且失败可见；401／403 或身份失效不能继续派发。保留已有正常消费、空项目列表和满容量行为的有效断言，不为了旧 `consume → projects → capacity` 精确调用顺序维持不合理前置关系。不启动真实项目、Server、数据库或模型来复现，不跑全套测试。
