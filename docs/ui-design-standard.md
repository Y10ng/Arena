# 全站 UI 设计规范：以 Cyber 工作台为参考

> 状态：2026-10-14 建立，作为 Arena 全站后续 UI 设计与实现的统一规范。本轮只编写文档，不表示已有页面全部符合规范，也不授权立即改造全站、构建或启停服务。
>
> 本文遵循 [AGENT.md](../AGENT.md) 的产品目标、前端约束与改动边界，集中维护布局、视觉和交互标准。具体任务方案只补充业务信息优先级、必要差异及本轮范围，不再各自复制一套颜色、尺寸和组件规则。

## 1. 设计方向与适用范围

**平台整体参考 Cyber 工作台的设计布局和视觉样式，而不只是复测页面使用相似配色。** 项目、工作区、漏洞成果、复测、资料、模型、Worker、系统设置及其弹窗／浮层均使用同一设计语言；登录、空态和错误页也不能成为另一套皮肤。

目标是长期使用的专业工作台：紧凑但不拥挤、层级明确、阅读舒适、操作位置稳定。参考的核心是近黑／炭灰的表面层次、柔和蓝色强调、细边框、克制圆角、清晰文字，以及与任务相配的表格、主从阅读和一体化编辑布局。

- **统一设计语言，不强制统一页面形状。** 任务列表以表格为主，资料阅读可以左列表右正文，运行工作区围绕当前工作与成果组织；不能把一个参考页面套到所有功能。
- **信息与操作优先，装饰退后。** 不用巨幅标题、渐变横幅、霓虹、发光边框、满屏统计卡片或多层卡片表达“高级感”。
- **不照搬业务机制。** 不因参考站存在组织、套餐、配额、资料分类或任务步骤就引入它们；不得把内部协议和无必要配置前置给用户。
- **保留 Arena 身份与数据边界。** 不复制 Cyber 的品牌、Logo、账号、水印、付费素材、登录态或业务内容。界面使用简体中文和 Lucide，保留必要技术术语，不新增 i18n 或另一套图标／组件库。
- **规范不是全仓改造授权。** 新增或修改界面时按本规范推进；共享主题调整与存量页面统一需要明确实施范围，不借一处功能改动重写整个前端。

## 2. 参考依据：观察与设计约定分开

参考站为 <https://cyber.chainreactors.cn>。已有观察依据来自 [漏洞复测方案第 9.1 节及第 13 节](specs/vulnerability-retest-design.md)：2026-10-14 的先前会话记录了实际浏览器观察、截图查看与 computed styles 取值。本规范编写轮未重新登录或测量参考站，不能把历史记录说成本轮现场验收。

| 参考范围 | 已记录的观察 | Arena 采用方式 |
| --- | --- | --- |
| `/tasks` 任务页 | 紧凑标题与操作、筛选、一整块满宽表格 | 项目／任务／复测等管理列表采用相同信息层级，不改成装饰卡片墙 |
| `/references` 资料页 | 左侧列表、右侧正文阅读 | 资料、知识、输入与证据阅读按需要采用主从布局，不泛化成所有列表的结构 |
| 新建任务弹窗 | 宽编辑区域，工具条／正文／资料底栏组成一个整体 | 正文驱动的创建／编辑动作使用一体化编辑器与稳定底部操作栏 |
| Materials 浮层 | 候选资料与已选资料分区 | 有实际候选来源时才分区；只有上传文件时展示真实文件列表，不虚构资料库 |
| 工作台视觉 | 近黑／炭灰、柔和蓝、细边框、清晰小字号、克制圆角和阴影 | 作为全站共享视觉基线，不复制站点品牌或业务对象 |
| 未观察的功能 | 没有足够依据证明其运行详情、管理设置或全部响应式布局 | 下文对这些页面的组织是 Arena 的设计约定，不宣称逐页还原 Cyber |

不以“使用了深色主题”“有蓝色按钮”或“改成左右两栏”代替整体一致性。参考站若变化，以经过确认的设计方向为准，不自动追随线上每次改版。

## 3. 视觉基线与共享 tokens

### 3.1 颜色与表面层次

以下深色数值来自上述历史观察，作为 Arena 的目标基线，不表示当前 tokens 已采用，也不是必须逐像素复制的品牌色规范。实际实现集中映射到共享语义 tokens，保证正文、控件、浮层及不同状态的对比度；不得在各功能页重复硬编码。

| 语义 | Cyber 观察值／特征 | Arena 使用约定 |
| --- | --- | --- |
| 页面底色 | `#101114` | 最低层画布，覆盖主工作区域，不在每个页面另造背景 |
| 侧栏 | `#15171b` | 与画布轻微区分，靠表面和细分隔线组织，不用厚阴影 |
| 面板／弹窗 | `#1e2025` | 承载主要内容；输入区、编辑区可比面板低一级，避免面板中反复嵌套面板 |
| 主强调色 | `#65a1e6` | 主要按钮、选中态、链接和焦点；不是所有标题／图标都染蓝 |
| 选中导航 | 蓝色约 15% 透明底 | 以浅底、文字和图标共同表达，不能只靠一条难辨认的线 |
| 主文字 | `#ebedf0` | 正文与关键值；次级文字用现有语义 token，不能降到难以阅读 |
| 边框 | 低对比细线，弹窗可带轻微蓝灰 | 区分相邻层次；默认不是发光描边，焦点边界必须清楚 |
| 状态色 | 与品牌强调分开 | 成功／警告／错误沿用语义色和文字，蓝色不代表成功或漏洞已确认 |

- 深色模式以这组视觉关系为参考，浅色模式保持同一结构、密度和交互，用现有浅色语义色实现足够对比；不把深色十六进制值机械套到浅色。
- 保留用户主题偏好，不为参考 Cyber 强制切换全站主题。一次局部功能改动也不能偷偷改默认主题。
- 阴影主要用于弹窗、Popover 等浮层；平面列表与表单优先靠留白、表面明度和细线。避免大面积模糊、玻璃效果和层层高投影。
- 当前主题与目标有差距时，在明确的共享样式实施范围内统一 tokens／组件；不要持续复制“某页面专用 Cyber 主题”。

### 3.2 字体与信息层级

保留现有字体栈，不为仿站下载字体。以下是全站目标尺度，按中文内容与阅读任务选择，不为凑参考尺寸压缩文字。

| 场景 | 默认目标 | 用法 |
| --- | --- | --- |
| 页面主标题 | 约 20px、字重 600 | 简短名称，不写成长段说明，不在普通工具页使用营销式大标题 |
| 区域标题 | 14–16px、中等至半粗 | 区分内容分区，不让每个字段都像一个标题 |
| 列表／控件正文 | 13px、行高约 1.5 | 保持扫读密度；主要名称与状态不能挤成难读小字 |
| 报告／授权范围／长正文 | 14–16px、行高约 1.7–1.85 | 阅读优先，段落有间距，宽屏限制合理行长 |
| 标签与辅助信息 | 12px | 字段标签、时间等次级信息，仍需足够对比 |
| 低频技术元信息 | 11px 可用 | 只用于非关键元数据；不用于主要按钮、错误原因和用户必须阅读的正文 |
| ID／报文／代码 | 现有等宽字体 | 与中文说明分层，长串可换行或在自己的区域横向滚动 |

### 3.3 间距、尺寸与形状

下列除明确标注的历史观察值外，都是 Arena 的设计约定；通过现有 tokens／组件尺寸表达，不逐处硬编码。

- 使用现有 4px 基础间距：4／8／12／16／24／32。默认页面内边距约 24px，窄屏约 16px；区域间距 16–24px，关联控件间距 8–12px。
- 侧栏宽度参考 248px，选中导航高度约 39–40px；保留已有折叠／移动导航能力，不为了一个页面反复改全站 Shell。
- 普通控件采用紧凑、易命中的高度，通常 32–36px；触控场景扩大操作区域，不以缩小图标和点击区换密度。
- 表格正文行通常 48–56px，允许单行紧凑或双行扩展；这是 Arena 建议，不是 Cyber 表格行高实测。长内容不撑坏整行，关键信息仍可完整访问。
- 控件圆角以约 8px、标签约 6px、主要面板约 8–12px 为参考；按现有语义尺寸复用，不把所有元素做成胶囊。普通状态 Badge 不做大按钮外观。
- 以细边框、合适留白和稳定对齐形成层级，不靠给每块正文套 Card。一个主要任务区域优先一个外层容器，内部用分隔和标题组织。

## 4. 全站骨架与导航

- 使用稳定的应用侧栏、页面标题区和主内容区。侧栏承担全站导航，页内 Tabs 承担同一对象／任务的内容切换，面包屑承担层级与返回；不要重复三套相同菜单。
- 普通页面标题左侧为名称与必要短说明，右侧为最主要动作；筛选或子导航在下一层。标题、工具条、表格和正文的左右边线对齐。
- 页面通常保留一个明显的主要动作，其余动作降为次要按钮或菜单。危险动作与高频操作分开，不把删除、停止等藏在只能靠颜色识别的图标中。
- 侧栏、面包屑、命令面板与页面标题使用一致中文名称；显示权限与服务端授权分别正确，隐藏菜单不代替鉴权。
- 内容宽度按任务分配：管理表格利用可用宽度，正文阅读控制行长，配置表单限制到舒适的编辑宽度。不能给所有页面强加同一个窄容器，也不能让单列短表单横跨超宽屏。
- 配置只提供完成任务所需的入口，不增加形式化前置步骤。例如专用复测 Worker／模型在复测配置中管理，不能为了“页面一致”强制用户去创建普通 Worker 或项目组。

## 5. 按任务采用页面模式

### 5.1 管理列表：紧凑满宽表格

适用于项目、计划、复测、漏洞以及需要多字段比较的模型／Worker／配置条目。

- 基本顺序为“标题与主操作 → 筛选／搜索 → 一块 DataTable → 分页”。不在列表前默认堆统计卡片；只有真实、直接服务当前动作的汇总才保留。
- 名称列是阅读入口，状态／结果／时间对齐稳定；次级 ID、来源和说明弱化，不与名称争夺空间。长名称可截断，但能打开详情或以可访问方式查看完整内容。
- 搜索、筛选和排序须有真实数据能力，明确精确匹配或全文检索；没有接口支持就不画假搜索框或无效页签。
- 行点击与行内按钮各自独立，不嵌套交互元素。打开详情后返回，保留合理的筛选、分页、选中与滚动位置。
- 数据少不等于应该换成大卡片。只有对象以独立内容块阅读且不需要逐列比较时才选择卡片布局。

### 5.2 资料与证据：主从阅读

适用于知识资料、文件材料、输入原件、报告与证据切换。

- 左侧是可扫描的资料导航，右侧是主要阅读区；列表不应占掉正文的大部分宽度。各自有清楚的滚动归属，不能让多层滚动相互争抢。
- 顶部清楚展示当前文件名、资料身份、可用操作和必要状态。原件、派生材料、历史证据与本次证据不能只靠颜色区别。
- 文件清单、下载、预览和原字节访问分别按真实能力提供。预览截断要注明；不能把摘要、替换字符或缩略图冒充完整原件。
- 只有一个资料或可用空间不足时可以单栏阅读，不为凑左右布局保留空列表。窄屏以“选择资料 → 阅读 → 返回资料列表”的明确路径替代被压扁的两栏。

### 5.3 项目／运行详情：当前工作与结果优先

此处是 Arena 的业务布局约定，不是声称已观察到 Cyber 对应详情页。

- 顶部集中对象名称、简短真实状态、核心操作；第一屏回答“当前在做什么／为什么等待、已经得到什么、下一步能做什么”。
- 用少量有业务意义的 Tabs 或稳定分区承载结果、输入、执行记录和历史。不是每个字段一张卡片，也不把全部日志和 JSON 平铺在首屏。
- 运行时优先展示实际活动与已有成果；终态优先结果、证据和限制。没有合法结果时明确说明，不用空结果面板或假进度填满屏幕。
- 证据／过程需要同时对照时可以分栏；纯阅读详情不强制长期保留侧边诊断栏。宽屏多栏应有实际阅读收益，窄屏按优先级降为单栏。
- 服务健康、执行状态、业务结论、环境回收是不同事实，分别表达；进程启动不代表模型正常，停止请求已接受不代表执行已停止，未复现不代表已修复。
- 技术 ID、完整错误、时间戳、协议字段按需展开，保留原文与访问路径。未知、过期快照、响应未确认等关键提示在折叠态仍可见。

### 5.4 创建与编辑：正文和主要输入优先

- 可在当前列表上下文完成的创建／编辑优先使用 Dialog；需要长期编辑、复杂深链接或大规模资料操作时用独立页面。共用输入与提交逻辑，不维护两套同义表单，不强制所有创建都改弹窗。
- 正文驱动的大弹窗参考约 896px 宽；这是历史参考值，不是所有 Dialog 的统一宽度。简单确认与短表单按内容使用已有较小尺寸，不能为了统一而撑大。
- 布局分为稳定标题栏、可滚动内容区、底部操作栏；弹窗高度受视口约束，不写死参考截图高度，保存／取消始终可到达。
- Markdown 编辑器把工具条、编辑／预览、正文、资料底栏置于一个外边框内。正文内边距可参考 18–20px，正文约 14px／26px 行高，初始编辑高度约 180–240px；内容较多时允许扩展，不让工具条抢占主要区域。
- 文件、附件数量和上传状态在资料入口收起后仍可见；浮层关闭不丢失正文、File、上传队列或已选项。只有实际存在候选资料时才显示候选／已选两区。
- 必需输入可见，高级参数按需展开；相关字段可以并排，长正文和错误不要塞在窄列。避免为了制造“流程感”把一个简单动作拆成多步向导。
- 离开有未保存内容的编辑区时准确提示；上传中、请求提交中、受理结果未知分别处理。未知结果不能悄悄生成新请求或显示假成功；不得将敏感正文默认写入浏览器持久存储。

### 5.5 配置页：配置一处，结果可理解

- 默认先显示主要配置与当前状态；相关的访问令牌、历史和低频高级项放次级分区／Tabs，不将所有编辑表单同时展开。
- 同一事实在一处编辑，摘要和其他页面读取同一来源。不让用户在 Worker、模板、集成和任务里重复填写同一模型／资源配置。
- 保存按钮靠近所属表单，保存反馈区分处理中、成功和失败；失败保留输入，并说明配置影响新任务、排队任务还是当前执行。
- 必须清楚区分“配置已保存”“连接已验证”“实际执行可用”；没有对应证据就不显示绿色已就绪。
- 凭据采用既有受控输入与一次性展示，不预填读取到的明文，不进入 URL、普通状态消息、日志、截图或浏览器持久缓存。

### 5.6 登录、空态与异常页

- 复用全站文字、控件、间距、圆角与表面层次，保留 Arena 品牌；不另做一张与工作台割裂的营销页面。
- 空态简短说明“还没有什么”以及实际下一步；无权限、无结果、筛选无匹配、加载失败不能全写成“暂无数据”。
- 错误页面说明影响和可执行动作，详细诊断按需查看；不使用巨幅插画、无关宣传或整屏调试堆栈。

## 6. 控件与交互细节

- **按钮**：主要／次要／文字／危险层级统一；图标与文字间距固定，图标按钮有可访问名称。禁用原因不能只藏在 disabled 控件的 tooltip 中。
- **输入**：标签、当前值、帮助与错误分层，必填规则准确；不让 placeholder 代替字段标签。错误靠近对应输入，长中文说明正常换行，不推走提交按钮。
- **Select／菜单**：选项可扫读，选中、禁用、加载、无结果有文字反馈；长名称可完整访问。不能仅在鼠标悬停时才知道实际选项或限制。
- **Tabs**：用于同一对象的视图切换，不用作无关页面的第二侧栏；选中态、焦点态明确，避免每个标签都像独立的大按钮。
- **Dialog／Drawer／Popover**：按动作语义选择，资料小工具用 Popover、完整编辑用 Dialog、上下文详情可用 Drawer。关闭最上层不连带清空底层表单；焦点回到合理触发位置，Esc 与背景交互符合共享组件约定。
- **Portal**：浮层不一定继承页面祖先样式，主题、字号、层级与尺寸通过共享组件和语义变量贯通；不得出现正文是统一工作台风格、下拉和弹窗却回到另一套默认皮肤。弹窗内部触发的下拉／资料浮层应位于其所属弹窗及遮罩之上，并遵守同一焦点边界；用共享层级与组件上下文处理，不逐页堆 `z-index:99999`。当前组件对层级 token 的使用并未全部统一，不能假定已有 Popover／菜单在任何 Dialog 中都自动正确。
- **反馈与动效**：轻量反馈不抢阅读；需持续处理的错误在页面保留，不能只靠瞬时通知。尊重 reduced-motion，避免闪烁、弹跳和无意义加载动画。
- **键盘与可读性**：焦点可见，Tab 顺序符合内容顺序，正常缩放时仍可操作；状态不只靠颜色，关键正文与控件保证足够对比。密度目标不能凌驾于可访问性。

## 7. 响应式、滚动与数据更新

- 以扣除侧栏后的实际可用宽度判断布局，优先复用现有断点，不为每个页面发明一组不同断点。
- 宽屏不无限拉长阅读行，窄屏不强撑多栏；页面工具条和动作按组换行，优先保留名称、状态与主要操作。
- 表格需要横向滚动时只让表格容器滚动，次要列可转详情；不让整个应用横向漂移。正文换行，报文／代码在自身区域按实际阅读需要换行或横向滚动。
- flex／grid 的可收缩区域设置正确的最小尺寸与滚动边界。不能用外层 `overflow:hidden` 掩盖被裁掉的按钮、正文或浮层。
- Dialog、Drawer 和资料浮层限制在视口内，长内容独立滚动；底部操作栏不遮住最后一项，移动端软键盘出现后仍能访问关键操作。
- 刷新保留当前阅读位置、输入与选中项；后台更新不重置整页。首次加载、局部刷新、旧数据和刷新失败分别反馈，不能一次错误就把已有资料清空。
- 仅按真实业务需要更新活动记录，终态停止不必要轮询；不能为了“实时感”增加推送系统或模拟进度。

## 9. 实施与验收边界

1. 接到具体 UI 任务时，先确定该页主要信息、主要动作和适用模式，再核对当前共享组件；不是重新设计全站或先做一套独立效果图。
2. 在明确范围内贯通页面、共享组件和所属浮层；如果需要改共享默认值，先说明实际受影响范围，保留已有交互与普通任务行为。不以“只是换样式”忽略全站影响。
3. 优先在实际 Arena 页面直接检查受影响区域的层级、点击、焦点、阅读、滚动及必要窄屏情形。参考站截图、CSS 值相似、组件渲染或构建成功都不等于实际页面符合规范。
4. 选择最短、能判断本次改动的验证方式；不默认全量测试、浏览器尺寸矩阵或新增视觉验收平台。无需为看布局启动真实任务、访问目标或调用付费模型；验证使用非敏感资料，凭据不得进入截图。
5. 报告区分设计规范已写、代码已实现、实际系统已加载、页面已观察及用户已确认。没有现场证据的部分明确待验收，不宣称“全站已经统一”。

本规范不是每次必须逐项填写的检查表。验收核心是：**使用者能在不同功能间保持一致的操作习惯，迅速找到当前工作、有效结果和下一步动作；视觉整体接近 Cyber 工作台的克制、清晰与密度，而不是只有局部配色相似。**
