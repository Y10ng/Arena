# 状态与流程滥用测试

业务流程通常是多步状态机：注册 → 登录 → 下单 → 支付 → 确认。漏洞常出在服务端没有在每一步强制校验"前置状态已达成"。

## 状态机篡改

- 直接跳到流程后段：跳过"支付"直接 `POST /api/order/confirm`，看是否确认成功。
- 把状态参数改回前态：`status=pending` 改成 `status=paid`，看是否解锁后续。
- 重复执行只应一次的步骤：重复调用"确认收货"刷积分/刷余额。

## 跳步与乱序

- 打乱步骤顺序：先调用第 3 步再调用第 1 步，看是否通过。
- 跳过校验步骤：如跳过"验证邮箱"直接"重置密码"。
- 用前一步的 token/nonce 用到后一步。

## 竞态与 TOCTOU

- 同一请求**并发**发多次：余额扣减、抽奖、领券、积分变更类操作常因非原子导致多扣/多发。
- 经典 TOCTOU：检查（check）与使用（use）之间有时间窗，并发插入另一个操作。
- 测试手法：用脚本/工具（如 curl 并行、自定义并发脚本）对同一 endpoint 同时发 N 个请求，观察是否出现"超出余额的成功"或"重复到账"。

## 判定要点

- 跳步后后段操作成功 → 流程状态校验缺失。
- 并发后结果与串行不一致（多扣/多发/重复确认）→ 竞态成立。
- 状态参数被篡改后服务端按篡改值执行 → 服务端信任了客户端状态。

## 证据

- 竞态：保存并发脚本 + 每个请求的响应 + 最终账户/资源状态快照。
- 跳步：保存跳过的步骤序列 + 后段操作的成功响应。
- `fact.description` 写明：从哪个状态跳到哪一步，或并发多少次得到什么异常结果。
