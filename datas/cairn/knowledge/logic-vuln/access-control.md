# 访问控制与越权测试

访问控制缺陷是逻辑漏洞中最常见的一类：服务端没有正确校验"当前用户能否对该资源/功能执行该操作"。

## 三种主要形态

- **水平越权（IDOR）**：同级别用户互访对方资源。例：`GET /api/orders/123` 改成别人的 order id 仍能读。
- **垂直越权**：低权限用户访问高权限功能。例：普通用户调用 `/admin/users/delete` 成功。
- **功能级访问控制缺失**：UI 隐藏了入口，但 API 仍可直调。例：前端不显示"导出全部"按钮，但 `POST /api/export-all` 直接可用。

## 测试方法

1. 准备至少两个不同角色/账号的会话（A、B），必要时一个管理员会话。**单一身份无法证明越权**——越权的本质是"换身份后本不该通的还能通"。
2. 用 A 走一遍合法流程，记录涉及到的资源 id、端点、参数。
3. 把 A 的请求里的**资源 id 换成 B 的**（水平），看是否返回 B 的数据或能操作 B 的资源。
4. 用低权限会话直接调用高权限端点（垂直），看是否被拦截。
5. 对前端隐藏的功能，直接用 API 重放（功能级）。
6. 检查 id 是否可枚举（自增整数、可猜测 UUID）；可枚举放大越权危害。

## 角色矩阵

对每个待测端点，跑一遍角色矩阵并记录每个角色的结果：

| 端点 | 匿名 | user-a | user-b | admin |
| --- | --- | --- | --- | --- |
| GET /api/orders/{id} | 401 | 200 自己 | 200 他人（IDOR） | 200 |
| POST /admin/users/delete | 401 | 403 | 403 | 200 |

- 水平越权：user-a 能读/改 user-b 的资源。
- 垂直越权：user-a/b 能调 admin 端点。
- 把矩阵结果以 `coverage:` 事实落图，避免重复测、便于 reason 决策。

## 判定要点

- 返回了不该看到的数据 → 水平越权成立。
- 低权限操作成功 → 垂直越权成立。
- 必须对比 baseline（自己访问自己的资源正常返回）与变体（访问他人资源），两者响应差异才能定性。
- 注意区分"共享资源"与"私有资源"——有些资源本就该跨用户共享，不算越权。

## 证据

- 保存：baseline 请求/响应 + 越权请求/响应，两组对照。
- `fact.description` 写明：角色 A 用什么请求访问了角色 B 的哪个资源，得到了什么本不该有的结果。
