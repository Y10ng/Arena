# 业务逻辑漏洞挖掘总览

业务逻辑漏洞（business logic vulnerability）源于应用**业务规则的错误实现或缺失**，而非签名可检测的缺陷。它无法被通用扫描器发现，必须理解"业务应当如何运转"后才能判断"哪里可以绕过"。

## 与扫描型漏洞的区别

- 扫描型：XSS、SQLi、已知 CVE、弱口令——靠 payload 字典与特征匹配。
- 逻辑型：越权、跳步、状态篡改、参数滥用、竞态——靠"理解业务流 + 变维重放"。

## 核心挖掘思路

1. **先建模业务**：入口点（端点/页面/API）、认证与会话模型、用户角色、业务流（多步工作流）、状态迁移、客户端/服务端信任边界。
2. **以覆盖矩阵驱动**：`端点 × 角色 × 流转状态`。优先补**未测单元**，逻辑漏洞常藏在未测的 (角色 × 端点) 或 (端点 × 流转状态) 组合里。
3. **单维变体重放**：先复现合法流程建立 baseline，再每次只变一个维度（角色 / 参数 / 状态 / 顺序 / 时序），对比 baseline 判断执行是否被绕过。
4. **可复现才算确认**：任何逻辑漏洞结论必须带可重放的请求/响应证据；无证据的"疑似"不算确认事实。

## 主要类别（详见同目录其他文件）

- 访问控制：IDOR、水平/垂直越权、功能级访问控制 —— `access-control.md`
- 状态与流程：状态机篡改、跳步、乱序、竞态/TOCTOU —— `state-and-flow.md`
- 参数篡改：类型混淆、负数/溢出、mass assignment —— `parameter-tampering.md`
- 证据与覆盖：覆盖矩阵、请求/响应取证 —— `evidence-and-coverage.md`

## 高价值优先级

当多个方向可选时，优先：能直接达成 goal 的 → 影响权限/资产的 → 可稳定复现的。低价值方向（如重复测已覆盖单元）应放进 `rejected_options` 并写明原因。
